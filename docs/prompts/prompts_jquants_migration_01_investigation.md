# J-Quants有料データ移行：実装前調査と設計

## 今回の作業
まだ本番コードの実装・変更はせず、既存コードと公式仕様を調査して、
段階的な実装計画を提示してください。
不明点を推測で埋めず、確認できた事実と提案を区別してください。

## 対象
- 主対象リポジトリ：kiyoto-aizu/trade-engine
- レポート側：kiyoto-aizu/trade-report
- ローカルで参照できないリポジトリは、その旨を報告してください。

## 契約
- J-Quants API
- 基本プラン：Light
- 株価 分足・ティックのアドオン契約済み
- APIキー取得済み
- キーの提示を要求しないこと。ファイルやログにも出力しないこと。

## 最終的な目的
1. 毎営業日、提供対象の全銘柄について日足・1分足を取得して蓄積する。
2. 契約上取得できる過去期間についても全銘柄分を補填する。
3. 日次更新と過去補填を並行でき、中断・失敗から再開できる。
4. バックテスト・分析・将来の戦略変更に再利用できるデータ基盤にする。
5. OHLC・出来高・売買代金など、提供された原本情報を失わない。
6. 既存Yahoo・自前収集データと実売買処理を壊さない。
7. 有料データやAPIキーをGit・公開レポートへ誤って出さない。

「全銘柄」は現在のスクリーニング対象だけを意味しない。
提供対象の商品範囲、過去時点の上場銘柄、上場廃止銘柄の取得可否を
調査し、含められる範囲と含められない範囲を明記する。

## 調査1：既存コード
以下の実装と依存関係を確認する。
- 設定と環境変数の読み込み
- HTTP共通処理が返す情報とエラー処理
- 日足・分足の取得処理
- MinuteBarなどのドメインモデル
- Parquet保存形式、重複・上書きルール
- バックテストと分析の入力経路
- 上場銘柄マスタと過去時点の対象銘柄の決定方法
- タスクスケジューラ、ログ、Slack通知
- .gitignoreとレポートへのデータ出力経路
- 既存テストの構成

変更候補には、実在するファイルパスと関数・クラス名を添える。

## 調査2：J-Quants公式仕様
公式ドキュメントを確認し、参照先と確認日を記載する。
Web参照できない場合は、確認不能な項目を明示して実装判断を止める。

確認項目：
- V2認証方式
- 日足・分足のエンドポイント、パラメータ、正確なレスポンス項目
- Lightと分足アドオンそれぞれの取得可能期間
- 当日分の提供・更新時刻
- 日付指定で全銘柄を取得できるか
- ページング、レート制限、エラー応答
- CSV／Bulkの利用条件と対象データ
- コード体系。英字を含む銘柄コードも考慮する
- 時刻・タイムゾーン・バーの開始／終了時刻の意味
- 約定なし、売買停止、休場、取得失敗の区別に使える情報
- 日足の調整係数・調整済み価格と分足の調整仕様
- データ保持、公開・共有、分析結果配信に関する利用条件

過去のチャットで提示されたAPI仕様やサンプルコードは、
正しいと仮定せず公式仕様と照合すること。

## 設計方針
- raw：取得した原本と安全な取得メタデータを保持
- canonical：固定スキーマのParquetとして保存
- feature：戦略依存の派生データとして分離
- rawには認証ヘッダー、APIキー、秘密を含むURLを保存しない
- 日次更新と過去補填で取得・変換・品質検査を共通化する
- 日次更新を優先し、過去補填がAPI枠を使い切らないようにする
- 全銘柄・長期間で小さなファイルが過剰に増えない保存単位を検討する
- ページング完了・検証・保存成功後にだけ取得完了とする
- 完了前データを利用側へ公開しない
- 再実行で重複・破損しない
- 全ページ取得済みの0件と、取得失敗・取得途中を区別する
- 無取引か取得漏れか判断できない場合は「不明」とする
- バックテストでは取得元、データ版、利用期間、欠損を記録する
- 既存データへの暗黙フォールバックは行わない
- 将来の訂正・再取得・再変換に対応できるようにする
