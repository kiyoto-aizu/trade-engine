## 総評

- 閾値の数字は初期値として妥当で、設計書・実装・テストの境界の扱い（Go ≤1% / Hold 1–5% / No-Go >5% など）も一致しています。
- 問題は「何で割るか」と「判定に使うデータが metrics JSON にまだ無いこと」です。
- 集計ツールは、現在の取得処理が書くJSONからは秘密情報・株価レコード・銘柄コードを出しません（ホワイトリスト方式）。ただし値の検証がありません（L1）。

## 重大

### S1. 集計ツールの「Go」が設計書の「Go」を意味していない

- 設計書§4の判定項目は9つですが、実装は status / 401・403 / 429率 / リトライ率 / 所要時間の5つだけです。警告・未知項目・銘柄数・空き容量は未実装です。
- そもそも metrics JSON にその値がありません。書き出しは `dataset` / `date` / `status` と通信まわりの計測値だけで、`error_category`・警告・銘柄数・実行モード（`raw_source`）は入っていません。
- 所要時間の上限が未設定（既定 `None`）だと時間判定が黙って飛ばされます。再現: `total=86400s` でも Go。テスト `test_elapsed_limit_applies_only_when_configured` がこの挙動を仕様として固定しています。CLIから上限を渡す手段もありません。
- 通信ゼロの実行（既存データ再利用 / `--canonical-only`）も Go になります。API健全性については何も言えていません。
- 提案:
  - 判定名を「部分判定」と分かる形にする。
  - 未評価の項目は Hold（例: `NOT_EVALUATED`）で出す。
  - 上限未設定は Hold（例: `ELAPSED_LIMIT_UNSET`）にする。
  - `error_category` / 警告 / 銘柄数 / `raw_source` を metrics JSON に追加する（別PRでも可）。

## 中

### M1. 429率・リトライ率の分母が小さすぎる

- 再現: 4リクエスト中429が1回（リトライで成功、status=COMPLETE）でも No-Go になります。1日分の取得はリクエスト数が少なく、比率の判定が不安定です。
- 取得クライアントは自前で1.2秒間隔に制限しているので、通常429はほぼ0のはずです。比率より回数（1回でも Hold、枯渇や複数回で No-Go など）のほうが実態に合います。
- リトライ率には429のリトライも入るため二重に数えています。429以外（5xx・通信エラー）のリトライ率に分けると独立した指標になります。
- 429を1回待つだけで120秒（`JQUANTS_429_WAIT_SECONDS`）が加わります。所要時間は `wait_seconds` を引いた値も併せて見てください。
- 所要時間の「上限」が未定義です。パイロット実測そのものにすると通常のばらつきで超えます。運用側の持ち時間で決めるほうが安全です。

### M2. 判定から動作への対応が未定義

- 429率 >5% は、§2が「補填を当日停止」、§4が「No-Go」、runbookが「当日停止」と書いています。日次・再開・補填それぞれで何を止めるかの表が必要です。
- 「再試行枯渇」「PARTIAL」は metrics JSON では区別できません（status は COMPLETE / ATTENTION / FAILED の3種類のみ）。
- 実装上、旧世代を保持した PARTIAL は FAILED ではなく ATTENTION（Hold）になります。設計書の「PARTIAL含む → No-Go」とずれています。

### M3. 再開の対象に EMPTY 系が漏れている

- `EMPTY_UNKNOWN` は「公開済み」扱いです。`list_incomplete_datasets()` には含まれず、別関数 `list_attention_datasets()` が担当しています。
- データ公開前の早い時刻に実行して空の結果が公開されると、通常の再実行では取り直されません（既存データとして扱われるため）。
- §3.1（4状態の列挙）と§3.6（COMPLETE以外すべて）も食い違っています。
- 決める必要があること: 休場日の正当な空と未公開による空の区別、営業日カレンダーの出どころ、日次の実行時刻（§8で判断待ちのまま）。

### M4. 同時実行の防止が不十分

- 実際に効いているロックは「データセット×日付」単位で、レート制限もプロセス内です。
- 日足と分足、日次と補填、手動のパイロット実行が別プロセスで重なると、同じAPIキーへのリクエストが倍になり429の原因になります。
- 全体ロックを置くか、スケジューラ側で「実行中なら新しく開始しない」設定にすることを設計に書いてください。

### M5. 停止状態の保持と 401/403 の切り分け

- 「全ジョブ停止」を、次のスケジュール実行が無視してしまう恐れがあります。停止状態を残す仕組み（停止フラグなど）が必要です。
- 403は、補填が契約範囲の端に着いたときにも出るかもしれません。その場合は補填だけ終了すれば足ります。提案:
  - 401: 全停止
  - 契約範囲内の403: 全停止
  - 範囲外の403: 補填の終了
- 契約範囲が固定か日々ずれるかは、公式仕様の確認が必要です（レビュアーは未確認）。

### M6. 取得処理とのつなぎ目が未テスト

- テストの metrics は手書きです。取得処理は `status_counts` を `http_status_counts` に付け替えて書いており、名前が変わると集計側が静かに劣化します。
- 既存の単日取込テストのfakeでJSONを作り、`summarize_run` に通すテストを追加してください。実際の「未計測」文字列もそこで確認できます。

### M7. バックアップとディスク基準

- 有料データはGit管理外で唯一のコピーです。契約が切れると再取得できない可能性があります。バックアップと整合性確認の方針を§8に入れてください。
- ディスク基準が2つあります（§2は10GB、§4は推定サイズの3倍/1.5倍）。どちらかに揃えてください。

## 軽微

- **L1 値の検証**: `status` などの自由文字列や、`request_count` に入れた辞書がそのままCSV・reasons に出ます（再現確認済み）。現在の取得処理では起きませんが、「出さない」を構造で保証するなら、数値列は数値のみ、status は列挙値のみ、それ以外は空にしてください。負数・NaN も同様です。テストが確認しているのは非ホワイトリストの「キー」だけなので、「値」の混入ケースも追加してください。
- **L2 一覧の見やすさ**: 同じ（dataset, date）の再試行がすべて並びます。「最新試行か」の列と連続FAILED数があると、§3.6の再開ルールに沿って読めます。
- **L3 終了コード**: No-Go があっても常に0です。スケジューラから使うなら、No-Go で非0にするオプションがあると便利です。
- **L4 文字化け**: CSVに「未計測」が入ります。Excelで開くなら `utf-8-sig` にしてください。
- **L5 `stage_breakdown`**: 検証・比較・ロック待ちの時間が含まれず、割合の合計が1になりません。「その他」を足してください。また、どこからも使われていません。
- **L6 データセット別の閾値**: 設計書は日足/分足で基準を分けるとありますが、評価関数にデータセットを渡す引数がありません。
- **L7 銘柄数の基準**: 補填は過去日なので「直近5営業日の中央値」ではなく、対象日の前後の営業日と比べるほうが合います。
- **L8 テストの抜け**: リトライ20%ちょうど、所要時間100%ちょうど、401/403の件数0、`request_count=0`。なお20%と100%ちょうどが設計書どおり Hold になることは確認済みです。

## docs/review-criteria.md への提案

1. ロック・並行制御・再開処理は「推奨」ですが、公開境界に触れる場合は「必須」にする。
2. 次の変更も必須に加える: 無人実行・自動再実行・スケジューラの導入 / API利用量・レート・リトライ設定の変更 / 依存パッケージの追加・CIの権限変更。
3. 「テストの追加・修正のみ」は不要扱いだが、既存の期待値の変更・削除は除外する（実質的に仕様変更）。
4. 重大/中/軽微の定義と「重大が未解決ならマージしない」を入れる。
5. レビュー依頼テンプレート（差分と全文の添付、前提、観点）を作る。
6. 「第三者」の定義（人間か別系統のモデルか）と結果の記録先を決める。
7. セルフチェックに「生成物がGit管理外であることの確認」と「出ないことを確かめるテスト」を足す（`data/jquants/metrics_summary.csv` が無視されることは確認済み）。
