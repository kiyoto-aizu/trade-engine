## 2. 今回の指摘

### 中

#### P1. 補填由来の403が、再開ジョブ経由で全停止に至る（N3 の修正の抜け）
- 現状: §2 の「403（契約範囲内の日付）」行は、補填は「補填のみ停止（フラグ保持）」、日次・再開は「停止（フラグ保持）」（全停止）です。一方、§3 規則6は補填の FAILED も再開対象にします。
- 起こりうる流れ: 補填が境界付近で403を受ける → 補填のみ停止 → その日付は最新試行が FAILED のまま再開対象に残る → 補填の停止フラグは再開を止めないので、再開ジョブが同じ日付を再実行 → 403 → 「再開の403」として全停止（日次も止まる）。人間が範囲内外を確認する前に起こりえます。契約範囲が日々ずれる場合（§9-2 で未確認）は、境界定数が古くなる分だけ起きやすくなります。
- 提案（どちらか）:
  1. 補填由来の日付が403を受けたら、台帳に「403要確認」と記録し、人間が確認するまで再開対象から外す。
  2. 再開ジョブの403は、対象日付の由来（日次/補填）で扱いを分け、補填由来なら「補填のみ停止」にする。

### 軽微

- **P2 `consecutive_failed` 列の意味が設計とずれている**: §2 は「同一 dataset、日付をまたいで数える」ですが、列は dataset×date ごとの連続数のままです（再現: 3つの日付が各1回失敗 → `[1, 1, 1]`）。列名を `consecutive_failed_same_date` などに変えるか、dataset 単位の列を足してください。dataset 単位で数える場合は、補填が日付を遡るため、パス順ではなくファイル名のタイムスタンプ順で並べる必要があります。
- **P3 休場日の「確認して台帳に記録」が人手前提に読める**: 週末・祝日は数が多いので、営業日カレンダー（§9-1）が決まったら、カレンダーで休場と判定した日は自動で台帳に記録する、と書いてください。カレンダーが決まるまでは、補填の日付列を営業日だけにする、という運用も選べます。
- **P4 新機能のテスト不足**: N8 の回帰テスト（内容が壊れた行が最新から漏れない）、`evaluation_complete` / `setup_reasons` / `active_seconds` の値、`inf` / `0` / 負数の上限、空ディレクトリの終了コードが未テストです。引数エラーのテストは `nan` だけです。
- **P5 空ディレクトリ**: ディレクトリは存在するが metrics が0件のとき、`--fail-on-no-go` でも終了コード0です（再現）。「実行が1件も無い」ことをゲートにしたい場合は、最新 metrics の鮮度チェックが別途要ります。必須ではありませんが、運用で使うなら §5 に一言あると誤解がありません。
- **P6 停止表の細部**:
  - Hold の動作が、429以外は書かれていません（他リトライ3〜9回、所要時間70〜100%）。補填側でどうなるかを書いてください。
  - 日次・再開が No-Go でも「○（継続）」なのは設計意図として妥当ですが、通知・記録の有無が書かれていません。
  - 品質検証失敗の補填「以降の日付も停止」は、遡る補填では「以降」が曖昧なままです（前回 N4 の一部）。
  - ATTENTION（Hold）が次の日付の処理を止めるかも未定義です。
- **P7 `active_seconds`**: `wait_seconds` が未計測（「未計測」）のとき、0として扱われ `total` と同じ値になります（再現: total 50 → active 50）。待ちゼロに見えるので、その場合は空欄にしてください。
- **P8 未対応のまま残っているもの**: 対応しない場合は、今回 `review-criteria.md` に追加された手順どおり、理由と記録先Issueを対応表に書いてください。
