## 2. 新たに生じた問題

### 中

#### N1. 回数ベースの閾値が、リクエスト量と連続性を見ない
- 再現: 600リクエスト中に429が3回（散発で、いずれもリトライで成功。0.5%）でも No-Go になります。
- クライアントは1ページあたり最大4回試行し（`JQUANTS_MAX_ATTEMPTS=4`）、429で120秒待ちます。そのため「429が3回」は、(a) 1ページで3回連続（枯渇まであと1回）とも、(b) 多数のページで散発3回とも読めて、現在は同じ No-Go です。(a) は危険信号ですが、(b) は分足のようにリクエスト数が多い場合は偶発の範囲かもしれません（分足の1日分のリクエスト数は未実測）。
- 提案:
  1. 数値は初期値のままでよい。No-Go に「同一リクエストで連続2回以上の429」を足す（#16 に `max_consecutive_429` などを追加）。
  2. 回数閾値を dataset 別に渡せるようにする（現状は所要時間上限だけ dataset 別）。
  3. #12 で、実行ごとに 429回数・他リトライ回数・request_count を記録し、分布から固定する。
- なお「429 が1回で Hold」は妥当です（自前で約1.2秒間隔にしているため通常は0のはず）。

#### N2. 所要時間判定で除く `wait_seconds` が、設計書の説明より広い
- `wait_seconds` は、(a) リクエストごとのレート制限待ち（約1.2秒）、(b) 429待機（120秒）、(c) 5xx・通信エラーのバックオフ、の合計です（`jquants_v2_client.py` L298 / L337 / L398-400）。評価は `total − wait_seconds` をすべて「実質時間」として上限と比べます。
- 再現: 総時間7200秒（うち待ち7000秒）、上限600秒でも Go になります。
- 設計書§4と runbook は「429待機を除く」と書いていて、実装とずれています。さらに上限は「運用側の持ち時間」（§4）、つまり壁時計時間で効くものです。待ちを除くと、持ち時間を超えても Go になります。
- 提案: 上限判定は `total`（壁時計）で行い、`total − wait_seconds` は別列で参考表示にする。429の影響は回数判定が担当する。待ち内訳の分割（429待機 / バックオフ / ペーシング）は #16 の候補。文書の表現も合わせる。

#### N3. 403 の「範囲内/範囲外」が、固定の境界日付に依存している
- §1 に契約境界が固定日付（日足 2021-10-21、分足 2024-10-21）で書かれ、§2 は「範囲外の403 → 補填終了、範囲内の403 → 全停止」です。一方 §9 は「契約範囲の動き方」を未確認としています。
- 範囲が日々ずれる契約だと、定数と実態がずれた日に補填が受けた403を「範囲内」と誤分類し、日次まで全停止になります（安全側ですが、無人運転では復旧が人間待ちになる）。
- 提案: 分類を日付ではなくジョブ種別で行う。日次・再開（直近の日付）の403 → 全停止。補填の403 → 補填のみ停止して人間が確認（境界到達の可能性）。境界定数の更新手順も §9 に入れる。

#### N4. §2 停止表に、未定義のセルと不足している行がある
- 凡例が「×=当日停止」なのに、401・403・ディスクは「全停止（停止フラグ保持）」です。「停止（フラグ保持）」と「当日停止」を分けてください。
- 429（補填）の「当日停止を検討」は規則になっていません。Hold のとき補填のみ当日停止、No-Go のとき再開も当日停止、のように決めてください。
- §4 の No-Go のうち、他リトライ ≥10、所要時間超過、status FAILED（1回）に対応する行が §2 にありません。Hold（ATTENTION）が次の日付の処理を止めるかも未定義です。
- 「連続FAILED 3回（同一 dataset/date）」は、同じ日付の再試行しか数えません。補填は日付が進むので、サーバー障害で日付ごとに1回ずつ失敗しても止まりません。dataset 単位（日付横断）の連続失敗も見てください。
- 品質検証失敗の補填「以降の日付も停止」は、遡る補填では「以降」が曖昧です。
- 「3回失敗で当日停止 → 翌日また3回」の繰り返しの上限（何日続いたら全停止・通知か）がありません。
- 5xx 連続・ネットワーク断・メンテナンスの扱いがありません。

#### N5. §3 規則6 と休場日の空が組み合わさると、再開が補填を押しのける
- 規則6は「最新試行が COMPLETE 以外」を再開対象とし、再開（P1）は補填（P2）より優先です。
- 休場日・週末の日付は空応答になり、EMPTY_UNKNOWN（status は ATTENTION）として公開されます。`--refresh` しても空のままなので、毎回「再開対象」に残り、API枠を使い続けて補填が進まなくなると読めます。営業日カレンダー未決のままでは、補填は有効にできません。
- 提案:
  1. 規則6に抜け条件を足す（「期待どおりの空」と確認・記録済みのものは再開対象外）。
  2. §9 を「実装着手の前提」（営業日カレンダーと実行時刻、全体ロック・停止フラグ、通知）と「実測後でよい」（閾値の最終値、補填予算、サイズ上限）に分ける。カレンダーは日次（P0）にも必要です。

### 軽微

- **N6 参照ずれ**: 「判断待ち（§8）」が §1-1、§2-1、§3 注意、§7 の4箇所にありますが、判断待ちの一覧は §9 です（§8 はテスト観点）。
- **N7 CLI の上限値**: `--daily-elapsed-limit` / `--minute-elapsed-limit` に `nan` や `inf` を渡すと、所要時間判定が常に Go になります（再現確認）。`0` は常に No-Go です。有限な正の値だけ受け付けてください。
- **N8 グループ化キーが内容由来**: `is_latest` / `consecutive_failed` のキーを JSON の `dataset` / `date` から作るため、検証に落ちた行が `("", "")` に集まります。再現: FAILED の行が「最新でない」扱いになり、`--fail-on-no-go` が 0 を返しました。キーはパス（dataset ディレクトリ・date ディレクトリ）から作るのが安全です。閾値の選択もパス基準なので揃います。
- **N9 終了コード**: `--fail-on-no-go` は、`--metrics-dir` が存在しなくても `runs=0` で 0 を返します（ゲートとして使うと誤った通過になる）。また終了コード1は Python の未処理例外と同じなので、No-Go とツールの異常を区別できません（例: No-Go は 2）。
- **N10 `partial_verdict` の表示**: 値が "Go" のままで、`not_evaluated` が全行で同じ項目です。「設計上の Go ではない」ことは列を読まないと伝わりません。`evaluation_complete`（`not_evaluated` が空か）列を足すか、"Go（部分）" のように区別してください。`--fail-on-no-go` は No-Go だけを見るため、「Go のときだけ補填を進める」運用には別オプションが要ります。また、CLI で上限を指定しないと全行が Hold になるので、設定不足（`ELAPSED_LIMIT_UNSET`）と実行品質の Hold を別列に分けると読みやすくなります。
- **N11 テスト**:
  - 結合テストは `http_status_counts` と `durations_seconds` 系のキーを検証していません（名前が変わっても通る）。401/403 の検出キーと、`total_seconds` / `acquisition_seconds` / `raw_size_bytes` を assert してください。
  - `test_other_retries_exclude_429_retries` は、429 だけで Hold になるため、除外していることを証明していません（例: 429=2、retry=12 → `OTHER_RETRIES_HIGH`）。
  - `--minute-elapsed-limit` と、dataset 別閾値の minute 側が未テストです。
- **N12 `stage_breakdown`**: 集計CSVに組み込まれず未使用のままです。使うか、PR本文の「工程別時間配分」を実態に合わせてください。
- **N13 ディスク基準**: チェックのタイミング（各ジョブ起動前か）と、サイズが分からない初回の扱いが未定義です。§4 の表には、実行後の判定（status・429 など）と、実行前のゲート（ディスク・ロック・停止フラグ）が混在しています。
- **N14 文言**:
  - `review-criteria.md` §1 の「新規決定」は、#12 で閾値を変えるときも対象になるよう「新規決定・変更」に。
  - 再レビューの要否基準がありません（例: 重大・中の修正、判定ロジックや停止表の変更を含む修正は再レビュー）。
  - 依頼テンプレートに【前回のレビュー】【対応表】を任意で足すと、今回のような再依頼がそのまま書けます。

## 3. 部分判定の考え方（観点3）

- 設計の表に「実装」列を持たせ、未評価項目を行ごとに `not_evaluated` へ出す形は適切です。未評価項目では判定を上げない（上げると全行が Hold になる）という割り切りも妥当です。
- 一方、評価済みなのに不確かな状態は Hold にする（未計測、不正値、上限未設定）のも、一貫した方針として読めます。
- 改善点は、「Go」という値が残ることと、設定不足の Hold が実行品質の Hold と混ざることです（N10）。

## 4. 回数ベースの初期閾値（観点4）

- 429 の 1回 Hold / 3回 No-Go: 1回 Hold は妥当です。3回 No-Go は日足（リクエストが少ない）では妥当ですが、分足では量の差が効きます（N1）。
- 他リトライの 3回 Hold / 10回 No-Go: 5xx・タイムアウトの基準値が未実測のため、妥当性は判断できません。初期値として置き、#12 で分布を見て決めるのが適切です。
- 共通: 回数判定に切り替えたのは正しい判断です。比率は1日分の取得ではぶれます。量と連続性の見方を足してください（N1）。
