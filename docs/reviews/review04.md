## 2. 今回の指摘（すべて軽微）

- **Q1 「補填由来の日付」の判定方法が未定義**: P1 の修正は、日付が補填由来かどうかで動作が変わります。台帳にジョブ種別（由来）を持たせるのか、「日次の対象窓（直近営業日）より古い日付」を補填由来とみなすのかを決めてください。実装前に決める事項として §9-1 に1行足すと漏れません。
- **Q2 カレンダー確定までの暫定運用が実行できない**: 「決まるまでは補填の日付列を営業日のみにする」は、営業日が分からないとできません。暫定は「平日（土日を除外）。祝日は空になるので人手で台帳に記録」と書くのが現実的です。
- **Q3 テスト2件の感度**:
  - `test_broken_content_cannot_steal_latest_and_new_columns` は壊れたJSON（読み込み不能）を使っています。読み込み不能な行は、旧コードでもパスからキーを作っていたので、このテストは旧バグを検出しません。守るべきシナリオは「JSONは読めるが、`dataset` / `date` が不正な行」です（再現: 2行とも `is_latest` が True なのが正しい）。
  - `test_dataset_wide_streak_spans_dates_in_timestamp_order` は `sorted(...) == [1, 2, 3]` で、行との対応を見ていません。並び順を日付順に誤っても通ります。ファイル名と値の対応（`1.json` → 1、`3.json` → 3）を assert してください。
- **Q4 Hold の扱いが、429とそれ以外で分かれている**: 429 の Hold は「補填は当日停止」、429以外の Hold は「その日の残りを予算の半分に縮小して継続」です。後者は未決の補填予算（§9-2）に依存します。表に Hold / No-Go を併記するか、429だけ扱いが違う理由を一言添えてください。
- **Q5 確認済みの No-Go を消す手段がない**: `--fail-on-no-go` はすべての日付の最新試行を見ます。人間が確認して台帳に「契約範囲外」と記録しても、metrics は FAILED のままなので、終了コード3が出続けます（再現: 古い失敗日が1件残ると、最新の日次が正常でも 3）。通知に使う前に、`--since` による期間指定、確認済み日付の除外リスト、当日の実行だけを見るオプションなどを決めてください（§9-1 の通知方法に紐づけられます）。
- **Q6 補填の有効化は #16 完了が前提**: `evaluation_complete` が False の Go を補填の開始条件にしない、と決めたため、#16 が終わるまで補填は開始できません。これは意図どおりだと思いますが、§1 規則2 か §9-1 に「補填の有効化は #16 完了後」と明記すると、運用の前提が読み取れます。
