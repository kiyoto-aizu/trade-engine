## 1. 目的と範囲

バックテスト・分析がJ-Quants canonicalデータを安全に参照するための契約を固定する。
対象は (1) canonical schemaの運用ルール、(2) 利用側の入力契約、(3) 暗黙フォールバック禁止の担保、(4) 公開系への出力禁止の再確認。
利用側（バックテスト等）の接続実装は範囲外で、接続時にこの契約を満たすこと。

## 2. canonical schema の運用ルール

現状の実装（`jquants_canonical_store.py`）: `SCHEMA_VERSION="1"`、datasetは `daily` / `minute`、列は `canonical_schema()` が定義する。
世代IDは dataset・日付・raw世代/hash・schema版・transformer版のhashで、manifestが `schema_version` を持つ。

### 2-1. 確定ルール

| ルール | 内容 |
| --- | --- |
| 破壊的変更の禁止 | 既存列の削除・改名・型変更・意味変更をしない |
| 変更は新バージョン | 列を変えるときは `SCHEMA_VERSION` を上げる。同じ版の中身を変えない |
| 追加のみ | 意味を変えない列の追加だけを許す。追加でも `SCHEMA_VERSION` を上げる（2026-10-24 決定。6章） |
| 既存世代の不変 | 版を上げても既存の世代・CURRENTは変更・削除しない（17章の世代方式を踏襲） |
| 未知項目 | 許可リスト外の項目はcanonicalへ自動追加せずrawに保持し、要確認として扱う（17章） |
| 版の記録 | 利用側は使った `schema_version` と `transformer_version` を結果に残す |
| 変更の検知 | `tests/test_jquants_consumer_contract_guard.py` が列名・型・順序・nullabilityの固定値と比べる。意図した変更では版とテストを同時に更新する |

`transformer_version` は変換ロジックの版で、schemaの版とは別に管理する。transformerの更新でschemaの列は変えない。

保存する列は、J-Quantsが返す項目のうち利用するものだけである。必要になったら、J-Quantsが返す項目を列として追加する（版を上げる）。
ATR・移動平均・ランキングなど自前で計算した値はcanonicalへ入れず、利用側が必要なときに計算する。
受け取った全項目は生データ（raw）に保持されるため、列の追加後は通信なしで再変換できる。

### 2-2. 版を上げたときの旧版データ（2026-10-24 決定）

`current_manifest()` は manifest の `schema_version` が実装の `SCHEMA_VERSION` と一致しない世代を検証失敗にする。
このため、版を上げた後の旧版世代は読まない。次の手順で新しい版へそろえる。

1. 保存済みの生データ（raw）から、通信なしで新しい版のcanonicalを作り直す（`--canonical-only` と同じ方式。17章）。
2. 旧版の世代は削除せず残す（既存世代の不変）。ただし利用側は読まず、常に最新の版だけを読む。
3. 作り直しが全期間で終わるまでは版が混在しうる。利用側は期間内の全日が同じ版であることを確認し、混在なら失敗させる。
4. 古い結果の再現: 追加列を除けば旧版と同じ内容になる。利用側は「使った列の一覧」を結果に残し、再現時はその列だけを使う。
   そのため、新しい版の既存列が旧版の既存列と一致することを、作り直しのたびに比較して確認する（読み取り層の実装時にテストを追加）。
5. 変換ロジック（`transformer_version`）の変更で既存列の値が変わる場合は、この方針の対象外とし、別途判断する。
6. 前提: 生データが残っていること。生データのバックアップ方針は18章 9-2。

## 3. 利用側の入力契約

利用側は次を明示して要求する。省略時の既定値で暗黙に決めない。

| 項目 | 内容 |
| --- | --- |
| `dataset` | `daily` または `minute` |
| `schema_version` | 要求する版。実装と一致しなければ失敗し、暗黙に読み替えない |
| 使う列 | 利用側が使う列の一覧。追加列を使わなければ旧版と同じ結果を再現できる |
| 期間 | 開始日・終了日（`YYYY-MM-DD`、両端含む）。営業日の自動補完をしない |
| 欠損日 | 期間内で検証済みCURRENTが無い日付を一覧にして明示する |

### 3-1. 利用側が残す情報

- 使用した世代: 日付ごとの `generation_id`・`schema_version`・`transformer_version`・`raw_generation_id`（manifest由来）。
- 欠損日リスト: 日付のみ。
- 欠損日の扱い（2026-10-24 決定）: 標準は、欠損日があれば一覧を表示して失敗する。欠損を許して続行するときは、実行のたびに明示オプションで指定する（設定ファイル・環境変数・既定値では有効にしない）。続行した結果には欠損日リストを必ず残す。取得失敗・検証失敗の日はオプションを指定しても失敗させる（3-2）。
- 欠損の理由（休場・未公開・取得失敗）はcanonical側で断定しない（16/17章）。区別は営業日カレンダー確定後（18章 9-1）。
- 結果に `dataset`・`schema_version`・使った列の一覧・期間・欠損日リスト・使用世代を含めて再現できるようにする。
  株価データ自体は結果へ複製せず、ID・hashで参照する。

### 3-2. 読み取り規則

- 読むのは検証済みの `CURRENT` 世代のみ。`ATTEMPT.json`・`staging`・未検証世代は読まない。
- manifest・Parquetの検証に失敗した日は欠損日にせず、エラーとして失敗させる（壊れたデータを欠損扱いにしない）。
- 利用側はcanonicalを書き換えない（読み取り専用）。

## 4. 既存Yahoo/自前データへの暗黙フォールバック禁止

J-Quants canonicalが欠けたときに、Yahoo系や既存の自前Parquetへ黙って切り替えない。
出所の異なる価格が混ざると、バックテスト結果の意味が壊れるため。

### 4-1. 担保方法

1. コード上の分離: `jquants_*` モジュールはYahoo系・既存バックテスト・公開生成をimportしない。
   逆に、Yahoo系・既存バックテスト・公開生成は `jquants_*` をimportしない。
2. 自動検査: `tests/test_jquants_consumer_contract_guard.py` がimport方向をAST解析で検査する。
   接続層を追加するときは、検査の許可リストにその1モジュールだけを明示的に加える（レビュー対象）。
3. 利用側の挙動: データ源は引数・設定で明示し、結果に記録する。
   J-Quants指定でcanonicalが欠けたら欠損日として扱い、他のデータ源で補わない。
4. 併用が必要な場合: 明示オプションのみ。既定は無効で、環境変数や既定値で有効にしない。併用した日付と範囲を結果に残す。

### 4-2. 現状の確認結果（2026-10-24）

`jquants_*` をimportするのは取得・変換・metrics集計系だけで、バックテスト・既存Parquet保存・Yahoo系・公開生成からのimportはない。
`jquants_*` からYahoo系へのimportもない。現時点で暗黙フォールバックにつながる接続はない。

## 5. 公開系（`trade-report`）への出力禁止の再確認

[公開レポート](../architecture/public-report-publication.md)の許可リスト方式を前提に、次を再確認する。

- 有料データの生値（OHLCV・調整後値・`UL`/`LL`等）と、そこから復元できる派生（価格系列、分足・日足を再構成できる値）を `trade-report` へ出さない。
- 公開してよいのは、同ドキュメントが許可した集計件数・理由コード・承認済みの診断画像などに限る。
  J-Quants由来の値を公開項目へ加えるときは、事前の所有者承認と許可リスト更新（レビュー対象）を必要とする。
- 3-1の入力契約情報は内部用とし、公開するときは許可リストに合う項目だけを選ぶ。
- 上記テストで、公開生成モジュール（`report_publication`）と `jquants_*` が互いにimportしないことも検査し、経路を作らせない。

## 7. テスト観点

- canonical schema固定: `daily`/`minute` の列名・型・順序・nullabilityが固定値と一致する。
- `SCHEMA_VERSION` が固定テスト内の版と一致する。
- import方向: `jquants_*` と Yahoo系・既存バックテスト・公開生成の間に依存がない。
- 入力契約・欠損日・世代記録・作り直し後の既存列の一致・版の混在検出は、読み取り層の実装時にテストを追加する（本書では未実装）。
