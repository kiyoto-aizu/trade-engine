## 1. 目的と範囲

バックテスト・分析がJ-Quants canonicalデータを安全に参照するための契約を固定する。
対象は (1) canonical schemaの運用ルール、(2) 利用側の入力契約、(3) 暗黙フォールバック禁止の担保、(4) 公開系への出力禁止の再確認。
利用側（バックテスト等）の接続実装は範囲外で、接続時にこの契約を満たすこと。

## 2. canonical schema の運用ルール

現状の実装（`jquants_canonical_store.py`）: `SCHEMA_VERSION="1"`、datasetは `daily` / `minute`、列は `canonical_schema()` が定義する。
世代IDは dataset・日付・raw世代/hash・schema版・transformer版のhashで、manifestが `schema_version` を持つ。

### 2-1. 確定ルール

| ルール | 内容 |
| --- | --- |
| 破壊的変更の禁止 | 既存列の削除・改名・型変更・意味変更をしない |
| 変更は新バージョン | 列を変えるときは `SCHEMA_VERSION` を上げる。同じ版の中身を変えない |
| 追加のみ | 意味を変えない列の追加だけを許す。追加でも `SCHEMA_VERSION` を上げる（2026-10-24 決定。6章） |
| 既存世代の不変 | 版を上げても既存の世代の中身は変更・削除しない（17章の世代方式を踏襲）。付け替えるのはCURRENTだけで、旧CURRENTは台帳に履歴として残す（履歴は付け替えを試みた記録で、失敗時の再試行で重複し得る）。付け替えは世代ごとに原子的に行い、作り直しが途中で失敗しても旧CURRENTが残る |
| 未知項目 | 許可リスト外の項目はcanonicalへ自動追加せずrawに保持し、要確認として扱う（17章） |
| 版の記録 | 利用側は使った `schema_version` と `transformer_version` を結果に残す |
| 変更の検知 | `tests/test_jquants_consumer_contract_guard.py` が、版ごとの固定表で列名・型・順序・nullabilityを比べる。列を変えるときは版を上げて新しい版の表を追加し、旧版の表は消さない。datasetの一覧、`TRANSFORMER_VERSION`、小さな固定入力の変換結果も固定する |

`transformer_version` は変換ロジックの版で、schemaの版とは別に管理する。transformerの更新でschemaの列は変えない。

保存する列は、J-Quantsが返す項目のうち利用するものだけである。必要になったら、J-Quantsが返す項目を列として追加する（版を上げる）。
ATR・移動平均・ランキングなど自前で計算した値はcanonicalへ入れず、利用側が必要なときに計算する。
受け取った全項目は生データ（raw）に保持されるため、列の追加後は通信なしで再変換できる。

### 2-2. 版を上げたときの旧版データ（2026-10-24 決定）

`current_manifest()` は manifest の `schema_version` が実装の `SCHEMA_VERSION` と一致しない世代を検証失敗にする。
このため、版を上げた後の旧版世代は読まない。次の手順で新しい版へそろえる。

1. 保存済みの生データ（raw）から、通信なしで新しい版のcanonicalを作り直す（`--canonical-only` と同じ方式。17章）。
2. 旧版の世代は削除せず残す（既存世代の不変）。ただし利用側は読まず、常に最新の版だけを読む。
   旧版のため読めない世代は、壊れたデータの「検証失敗」とは別の「旧版のため要再作成」として報告する。
3. 作り直しが全期間で終わるまでは版が混在しうる。利用側は期間内の全日が同じ版であることを確認し、混在なら失敗させる。
4. 作り直した世代ができたら、世代ごとにCURRENTを新世代へ付け替える（2-1）。
5. 追加列を除けば旧版と同じ内容になる。そのため、作り直しのたびに、新しい版の既存列が旧版の既存列と一致することを比較して確認する。
   この比較テストは、読み取り層（#18）をマージする前提条件とする。
6. 変換ロジック（`transformer_version`）の変更で既存列の値が変わる場合は、この方針の対象外とし、別途判断する。
7. 前提: 生データが残っていること。生データのバックアップ方針は18章 9-2。

#### 作り直し中の運用（dataset共通の版であることのコスト）

`SCHEMA_VERSION` は全dataset共通で、実装と一致しない世代は読めない。そのため、分足だけに列を足す場合でも、日足を含む全datasetが作り直し対象になる。

- 止まる期間: 作り直しが終わるまで、利用側（バックテスト等）は新しい版を読めない。作り直しは、止まる期間が短くなるよう日足から先に行う。
- 容量: 旧版の世代を残すため、作り直した分だけ保存容量が増える。作り直す前に、対象期間の現在の容量を確認して見積もる。
- 切り替えの目印: 無駄な作り直しが問題になる場合（例: 分足だけに列を足す必要が出た場合）は、dataset別の版管理を検討する（別Issueで判断）。

## 3. 利用側の入力契約

利用側は次を明示して要求する。省略時の既定値で暗黙に決めない。

| 項目 | 内容 |
| --- | --- |
| `dataset` | `daily` または `minute` |
| `schema_version` | 要求する版。実装と一致しなければ失敗し、暗黙に読み替えない |
| 使う列 | 利用側が使う列の一覧。追加列を使わなければ旧版と同じ結果を再現できる |
| 期間 | 開始日・終了日（`YYYY-MM-DD`、両端含む）。営業日の自動補完をしない |
| 営業日カレンダー | 営業日（区分1・2）と休場（区分0・3）を判定する元。読み取り層の前提条件で、取得・保存は #19 |

欠損日は入力ではなく、利用側が検出して出力する値である。検出ルールは次のとおり。

- 期間内の営業日（区分1・2）で、検証済みCURRENTが無い日を欠損日とする。区分0・3（休場）は欠損に数えない。
- 営業日カレンダーが無い、または期間を覆っていない場合は、判定できないため失敗する（暗黙に全日を営業日扱いしない）。
- 暫定で続行を許すときは、許す日付を実行ごとに明示指定させる。「何でも続行」にはしない。

### 3-1. 利用側が残す情報

- 使用した世代: 日付ごとの `generation_id`・`schema_version`・`transformer_version`・`raw_generation_id`（manifest由来）。
- 欠損日リスト: 日付のみ。
- 欠損日の扱い（2026-10-24 決定）: 標準は、欠損日があれば一覧を表示して失敗する。欠損を許して続行するときは、許す日付を実行のたびに明示オプションで指定する（設定ファイル・環境変数・既定値では有効にしない）。続行した結果には欠損日リストを必ず残す。
- 取得失敗・検証失敗の日はオプションを指定しても失敗させる（3-2）。取得失敗かどうかは、台帳（16章）に当日の取得試行が失敗として記録されているか、その日の `ATTEMPT.json` が失敗で残っているかで判定する。判定元の具体的な状態名は読み取り層（#18）で確定する。
- 欠損の理由（休場・未公開・取得失敗）はcanonical側で断定しない（16/17章）。休場は営業日カレンダーで判定し、営業日で世代が無く、取得失敗の記録も無い日は「未公開または未取得」として扱う。契約プランの範囲外（遅延・保有期間）による欠落との区別は、読み取り層（#18）で確認する。
- 結果に `dataset`・`schema_version`・使った列の一覧・期間・欠損日リスト・使用世代・`data_source`（例: `jquants`）を含める。
  株価データ自体は結果へ複製せず、ID・hashで参照する。
- 再現性（2026-10-24 決定）: 上記の記録は監査用であり、同じ条件の再実行で同じ結果になることは保証しない。再取得でCURRENTが変わることや、調整値（`Adj*`）が株式分割などで後から変わることがあるため。
  世代を指定して読むモードが必要になったら、別Issueで検討する（先送りであり、不採用ではない）。

### 3-2. 読み取り規則

- 読むのは検証済みの `CURRENT` 世代のみ。`ATTEMPT.json`・`staging`・未検証世代は読まない。
- manifest・Parquetの検証に失敗した日は欠損日にせず、エラーとして失敗させる（壊れたデータを欠損扱いにしない）。
  版の不一致による失敗は「旧版のため要再作成」として、壊れたデータの失敗とは別のメッセージにする（2-2）。
- 利用側はcanonicalを書き換えない（読み取り専用）。

## 4. 既存Yahoo/自前データへの暗黙フォールバック禁止

J-Quants canonicalが欠けたときに、Yahoo系や既存の自前Parquetへ黙って切り替えない。
出所の異なる価格が混ざると、バックテスト結果の意味が壊れるため。

### 4-1. 担保方法

1. コード上の分離: `jquants_*` モジュールはYahoo系・既存バックテスト・公開生成をimportしない。
   逆に、Yahoo系・既存バックテスト・公開生成は `jquants_*` をimportしない。
2. 自動検査: `tests/test_jquants_consumer_contract_guard.py` がimport方向をAST解析で検査する（`src` と `scripts`）。
   - `jquants_*` 側は、名前にjquantsを含むモジュールと共有設定（`src.config`）以外の `src.*` をimportできない（許可リスト方式）。相対import（`from . import x`）は、ファイルの置き場所から絶対名に直してから判定する。`from パッケージ import 名前` は「パッケージ.名前」で判定する。動的import（`importlib.import_module`・`__import__` の呼び出し）も検出する。
   - 限界: 直接のimportだけを検査する（共有設定が内部でimportするものは見ない）。`getattr(importlib, "import_module")` の形や `exec` は検出できない。
   - それ以外のモジュールは `jquants_*` をimportできない。
   - 接続層を追加するときは、検査の許可リスト（`CONNECTION_LAYER_ALLOWED`）にその1モジュールだけを明示的に加える（レビュー対象）。許可した接続層は、Yahoo系・既存バックテスト等をimportしないことも同時に検査する。
3. 利用側の挙動: データ源は引数・設定で明示し、結果に記録する。
   J-Quants指定でcanonicalが欠けたら欠損日として扱い、他のデータ源で補わない。
4. 併用: 現在は認めない（6-1）。認める場合は、実行ごとの明示オプションのみ（既定は無効、環境変数や既定値で有効にしない）とし、併用した日付と範囲を結果に残す。その判断は別途行う。

### 4-2. 現状の確認結果（2026-10-24）

`jquants_*` をimportするのは取得・変換・metrics集計系だけで、バックテスト・既存Parquet保存・Yahoo系・公開生成からのimportはない。
`jquants_*` からYahoo系へのimportもない。現時点で暗黙フォールバックにつながる接続はない。

## 5. 公開系（`trade-report`）への出力禁止の再確認

[公開レポート](../architecture/public-report-publication.md)の許可リスト方式を前提に、次を再確認する。

- 有料データの生値（OHLCV・調整後値・`UL`/`LL`等）と、そこから復元できる派生（価格系列、分足・日足を再構成できる値）を `trade-report` へ出さない。
- 公開してよいのは、同ドキュメントが許可した集計件数・理由コード・承認済みの診断画像などに限る。
  J-Quants由来の値を公開項目へ加えるときは、事前の所有者承認と許可リスト更新（レビュー対象）を必要とする。
- 3-1の入力契約情報は内部用とし、公開するときは許可リストに合う項目だけを選ぶ。
- 上記テストで、公開生成モジュール（`report_publication`）と `jquants_*` が互いにimportしないことも検査し、経路を作らせない。
- importの禁止だけでは足りない（2026-10-24 決定）。接続後は、J-Quantsから読んだ価格がバックテスト結果（約定価格・損益・曲線）を通じて、importなしでデータとして公開生成へ流れうるため。
  - 価格系列を含む公開経路はすでに動いている。分足の時刻と終値・買値・損切り・トレーリングの系列・実現損益額を載せる診断JSON（`data/charts/YYYY-MM-DD.json`）で、所有者の承認済み（[公開レポート](../architecture/public-report-publication.md)）。公開前の関門は `src/infrastructure/report_publication.py` の `public_chart_data()`（元データは `scripts/analysis/intraday_chart_payload.py` が生成）。
  - 上の「価格系列を出さない」は、J-Quants由来のものを出さないという規則であり、自前取得データの診断JSONの公開は別の承認で動いている。J-Quants由来の値がこの診断JSONの元データに混ざった時点で、有料データの公開になる。
  - 結果に出どころ（`data_source`。例: `jquants`）を必ず残す（3-1）。
  - 公開生成は「許可する出どころの一覧」方式にする。現行の出どころ（自前取得など）を明示的に許可し、一覧に無い出どころと、出どころの記録が無いものは落とす（記録が無い既存の結果も、一覧で明示した場合だけ通す）。J-Quants由来は、所有者の承認がない限り一覧に加えない。
  - この動作のテスト（`public_chart_data()` 側を含む）を、読み取り層（#18）をマージする条件に含める。

### 6-3. 営業日カレンダーの取得・保存（#19）

| 項目 | 内容 |
| --- | --- |
| 構成 | domain `jquants_business_calendar.py`（検証）、infrastructure `market_data/jquants_calendar_store.py`（保存・読み出し・`BusinessCalendarPort` 実装）、application `jquants_calendar_ingestion.py`、entrypoint `ingest_jquants_calendar.py` |
| 取得 | `markets/calendar` を `from`/`to` で取得（既存の `JQuantsV2Client`）。実API接続は `--allow-network` を付けたときだけ。出力は件数・区分別件数・期間のみで、キー・生応答は出さない |
| 保存 | `data/jquants/calendar/calendar.json`（`JQUANTS_CALENDAR_DIRECTORY` で変更可、Git管理外）。日付→区分のみ。生応答は保存しない。sha256付きで、一時ファイルから `os.replace` で原子的に置き換える |
| 検証 | 期間内の全暦日が揃うこと。重複日・期間外の日・日付形式不正・区分が0〜3以外は失敗し、保存済みの内容は変えない |
| 再取得 | 保存済みの日と区分が異なる場合は失敗し、`--refresh` を明示したときだけ上書きする。同じ内容の再実行は変更なし |
| 読み出し | `categories(start, end)` は保存済みの日だけを返す。未保存の日は含めず、`business_days_from_calendar` が「期間を覆わない」として失敗させる。保存ファイルが壊れていれば失敗 |
| 範囲外 | 契約範囲外の期間も、カレンダー自体はAPIの応答に従う（失敗は失敗として報告） |
