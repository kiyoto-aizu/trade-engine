# J-Quants 運用オーケストレーション設計（案）

状態: 提案（未実装・判断待ちあり）。前提: 設計書15/16/17、`runbook_jquants_pilot_one_day.md`。
本書は単日取込CLI（`ingest_jquants_single_day`）を日次運転・過去補填へ拡張する際の運用ルールを定める。
閾値はすべて初期値で、パイロット実測後に見直す。
第三者レビュー（PR #14）の指摘を反映済み。

## 1. ジョブ種別と優先度

| 優先 | ジョブ | 内容 |
|---|---|---|
| P0 | 日次更新 daily | 直近営業日の日足 |
| P0 | 日次更新 minute | 直近営業日の分足 |
| P1 | 再開 recovery | 未完了・要確認データセットの再実行（§3） |
| P2 | 過去補填 backfill | 契約範囲（日足 5 年 / 分足 2 年、日々ローリング。§2-2）の内側で、古い日付から補填する |

ルール:
1. 日次更新は常に補填より優先する。
2. 補填は日次更新が完了済み、かつ当日の1日あたり予算内の場合のみ実行する。
3. 補填は1日分（dataset×date）を最小単位とし、古い日付から進める（ローリングで古い日から先に取得不能になるため。2026-10-25 改訂、旧: 新しい日付から遡る。人間判断事項）。
4. 日足と分足は同時に走らせない。日次では 日足 → 分足 の順。
5. データセットロックを取得できない場合は待機せず、そのジョブをスキップして記録する（処理を奪わない）。

### 1-1. 同時実行の防止
既存のロックは dataset×date 単位で、レート制限もプロセス内に閉じている。
日足/分足、日次/補填、手動パイロットが別プロセスで重なると同一APIキーへのリクエストが倍増し429の原因になる。
実行基盤で「実行中なら新規開始しない」設定にするか、全体ロック（APIキー単位）を置く。
**決定（Issue #49、人間承認済み）**: 補填は全体ロックファイル（`JQUANTS_BACKFILL_STATE_DIRECTORY/backfill.lock`、排他作成、PID・取得時刻のみ記録）を取り、取れなければ待たずに終了（`LOCK_SKIPPED`）する。異常終了で残った stale ロックは自動で奪わず、人間が稼働中でないことを確認して削除する。日次更新・手動パイロットへの適用は日次の運用配線時に行う（現状は補填のみ）。

### 1-2. 日次更新ジョブの実装範囲（Issue #36）
`python -m src.entrypoints.run_jquants_daily [--date YYYY-MM-DD] [--publish-after HH:MM]`（実装: domain `jquants_daily_plan.py` / `jquants_daily_stop_policy.py`、application `jquants_daily_job.py`）。
- 対象日: 営業日カレンダー（区分1・2）の実行日のみ。休場（0・3）は HOLIDAY、`--publish-after` 前の営業日は NOT_PUBLISHED として区別してスキップする。カレンダーに無い日は営業日扱いにせず失敗（終了コード1）。`--publish-after` の既定は 17:00（日次の実行時刻 17:00 は人間が確定。実測: 日足は16:32以前、分足は16:32〜16:42の間に公開）。当日より前の日付を `--date` で指定した場合は時刻判定しない（時刻は JST。過去日は公開済み、未来日は NOT_PUBLISHED）。未公開時の再試行運用は維持する。
- 実行順: 日足 → 分足。各取込後に metrics を評価（Go/Hold/No-Go）して結果に記録する。
- 停止条件（§2 日次の列）: 401/403=停止（フラグ保持が必要と通知。フラグ自体は未実装）、400・品質検証失敗=その dataset のみ停止、連続 FAILED 3回（metrics から数える。ロック失敗は数えない）=当日の残りを停止、その他の FAILED=再開対象で継続、ATTENTION=継続。429 打ち切り（RATE_LIMIT_ABORTED）は、同じ API キーで枠が尽きた直後に続けて取りに行かないよう、当日の残り（分足）をスキップする（2026-10-30 人間決定。終了コードは 3 のまま）。dataset 単位の想定外例外（`STORAGE_OR_FORMAT_ERROR`）は結果に残し、他の dataset の結果は失わない。
- ロック取得失敗（`error_category=DATASET_ALREADY_RUNNING`）は待機せずスキップして結果に記録し、終了コード2。
- 終了コード: 0 / 2（ATTENTION・ロックスキップ）/ 1（失敗・停止）/ 3（429 打ち切り）。
- 未実装: 停止フラグの永続化、同一原因の当日停止3営業日連続の判定、全体ロック、スケジューラ登録、過去補填。
- 停止の効力は1回の実行の中だけ: 当日停止・dataset のみ停止は、同日の再実行を止めない。STOP_TODAY / STOP_JOB の通知も未実装（通知は 401/403 の stderr 1行と、取込側の 429 通知のみ）。無人実行（スケジューラ導入、#37）の前提条件とし、#37 で扱う（2026-10-30 人間決定）。
- 営業日カレンダーは `ingest_jquants_calendar` で更新する。日次の前に更新される前提で、未取得の日は CALENDAR_MISSING（終了コード1）になる。更新の主体・時刻は #37 で定める。
- ロックスキップの metrics 評価（`ERROR_CATEGORY_DATASET_ALREADY_RUNNING` が No-Go になる点）は #37 で扱う。
- 想定外例外（`STORAGE_OR_FORMAT_ERROR`）は metrics を書かないため、連続 FAILED に数えられず通知もない。同じ例外が毎日続いても当日停止に届かない。#37 で扱う。
- 連続 FAILED は、手動実行・補填を含む同一 dataset の metrics を日付をまたいで数える（§2 の趣旨どおり）。

## 2. 停止・減速条件（API枠制御）

動作はジョブ種別ごとに定める。
- ○: 継続
- 停止（フラグ保持）: §2-1 の停止フラグを立て、人間が解除するまで以降の実行も止める
- 当日停止: 当日の残りの実行だけ止め、翌営業日の実行は妨げない

| 条件 | 日次 | 再開 | 補填 | 備考 |
|---|---|---|---|---|
| 401 | 停止（フラグ保持） | 停止（フラグ保持） | 停止（フラグ保持） | 全ジョブ停止。人間判断で再開 |
| 403（契約範囲内の日付） | 停止（フラグ保持） | 停止（フラグ保持）。ただし補填由来の日付は補填のみ停止 | 補填のみ停止（フラグ保持） | 権限・契約の異常。補填の403は台帳に「403要確認」と記録し、人間が確認するまで再開対象から外す（再開ジョブ経由の全停止を防ぐ） |
| 400（契約範囲外の日付） | - | - | 補填を終了（実装: #49） | 実測(#12)で範囲外は 403 でなく 400。自前判定（§2-2）で事前除外するため通常は発生しない。発生は判定漏れ（境界到達）として、台帳に「契約範囲外」と記録し補填を終了、定数を確認する。metrics 評価は日付を知らないため 400 を一律 No-Go（`HTTP_400_SEEN`）とし、範囲内外の区別は §2-2 の分類で台帳側に残す |
| 400（契約範囲内の日付） | 当該ジョブのみ停止 | 同左 | 当該ジョブのみ停止 | 実装不具合・想定外（`UNEXPECTED_400_IN_RANGE`）。範囲外と区別して No-Go（metrics 理由 `HTTP_400_SEEN`）。自動リトライしない |
| 429（metrics上で1回以上） | ○（Hold。日次ジョブは 429 打ち切り時に当日の残りをスキップ。§1-2） | ○（Hold） | 当日停止（Hold） | 3回以上は No-Go。補填は1回でも当日停止。1実行内の429累計が `JQUANTS_MAX_429_PER_RUN`（既定3）に達した時点で、その実行の残りの取得を全て打ち切る（待機を続けない）。打ち切りは FAILED（raw は PARTIAL/FAILED、旧世代と CURRENT 保持、`--refresh` で回復）、`error_category=RATE_LIMIT_ABORTED`、metrics の `rate_limit_aborted=true` / `abort_reason=RATE_LIMIT_429_CAP`、評価理由 `RATE_LIMIT_ABORTED`（No-Go）、CLI 終了コード 3 + stderr に ALERT 1行 + Slack critical チャンネル（`SLACK_WEBHOOK_CRITICAL`）へ通知する（本文は dataset・日付・429 回数のみ。送信失敗は warning `SLACK_NOTIFY_FAILED` に残し、結果は変えない）。429 は調査対象であり、原因確認前に `--refresh` で再実行しない |
| 429以外のリトライ ≥10 | ○（No-Go） | ○（No-Go） | 当日停止（No-Go） | 3–9回は Hold |
| 所要時間が上限超 | ○（No-Go） | ○（No-Go） | 当日停止（No-Go） | 70–100%は Hold |
| FAILED 1回 | ○（再開対象） | ○ | ○（再開対象） | 再開手順（§3）で再実行 |
| 連続FAILED 3回（同一 dataset、日付をまたいで数える） | 当日停止 | 当日停止 | 当日停止 | 人間へ通知。補填は日付が変わっても連続とみなす |
| 5xx・メンテナンス応答が続く | ○（Hold） | ○ | 当日停止 | 内部リトライ（最大4回/ページ）後も失敗すれば FAILED として上記に従う |
| ディスク空き不足（§4-1） | 停止（フラグ保持） | 停止（フラグ保持） | 停止（フラグ保持） | 全停止 |
| 未許可の未知項目 | 当該ジョブのみ停止 | 同左 | 同左 | ExRT/MktCap は記録のみ |
| 品質検証失敗 | 当該ジョブ停止 | 同左 | 以降の日付も停止 | No-Go |

停止の繰り返し上限: 同一原因の「当日停止」が3営業日連続したら停止フラグを立て、人間の確認を必須とする。

Hold と No-Go の扱い（日次・再開が「○」でも記録は必須）:
- 日次・再開は Hold/No-Go でも継続するが、サマリCSVに記録し、No-Go は `--fail-on-no-go` で通知対象にする。
- 補填は Hold（429以外のリトライ3〜9回、所要時間70〜100%）なら継続し、1日の予算を縮小する（初期案、予算は §9-2）。
  429 は1回でも当日停止にする。理由は、429 が API 枠の枯渇を直接示し、継続すると日次の枠を食うため。No-Go は当日停止。
- ATTENTION（Hold）は次の日付の処理を止めないが、人間の確認対象として台帳に残す。
- 「以降の日付も停止」は、補填が日付を遡る場合も「その補填ジョブの残り全日付」を指す。
- `evaluation_complete` が False の Go は、補填の開始条件にしない（Issue #16 で WARNINGS / UNKNOWN_FIELDS / SYMBOL_COUNT、Issue #24 で DISK_SPACE を評価対象にした。旧形式の JSON では該当項目が未評価のまま＝False）。

契約境界の定数更新手順: 範囲外の400で補填が終了したら、①公式の契約範囲を確認、②`CONTRACT_YEARS` を更新、
③当該日を台帳に「契約範囲外」と記録、の順に行う。

「429 再試行枯渇」と「PARTIAL」は、現状の metrics JSON（status は COMPLETE/ATTENTION/FAILED のみ）では区別できない。
旧世代を保持した PARTIAL は FAILED でなく ATTENTION（Hold）になる。Issue #16 で metrics JSON に
`error_category`・`warnings`（列挙コードのみ）・`symbol_count`・`unknown_field_count`・実行モード（`raw_source`: fetch/existing/none）を
追加し、判定（`ERROR_CATEGORY_*` / `WARNINGS_PRESENT` / `UNKNOWN_FIELDS_SEEN` / `SYMBOL_COUNT_ZERO` / `FETCH_WITHOUT_REQUESTS`）と
集計CSVの列に反映した。コード以外の文字列は値として採用しない（コードは先頭が英大文字の英大文字・数字・`_` のみ。数字だけの銘柄コード風文字列は不可）。
書き出し側でも同じ判定を通し、非コードは捨てて `INVALID_WARNING_DROPPED` を記録する。銘柄数・未知フィールド数は「未計測」のとき null とし、未評価のまま残す。

割り切り（暫定）:
- `error_category` が `RATE_LIMITED` でも status が ATTENTION なら判定は Hold どまり。429 の当日停止は、429 件数の閾値（`RATE_LIMIT_429_HIGH`）側で扱う。
- 銘柄数0 は Hold（`SYMBOL_COUNT_ZERO`）。「休場日の空」と「未公開の空」の区別が未決のため、補填が休場日を含むと Hold が増え、人の確認対象が増える。Hold は次の日付を止めない。

なお 429 打ち切り（#17）に限り、`error_category=RATE_LIMIT_ABORTED` と `rate_limit_aborted` / `abort_reason` は実装済みで、「再試行枯渇」と区別できる。既定設定（上限3 < 1ページの最大試行4）では 429 だけで再試行枯渇（`RATE_LIMITED`）になる経路はなく、必ず打ち切りになる。打ち切りまでの最大待機は「(上限−1)回 × `JQUANTS_429_WAIT_SECONDS`」（既定で約240秒）。

終了コード（`ingest_jquants_single_day`）: 0=COMPLETE、1=FAILED、2=ATTENTION、3=429 打ち切り（FAILED の一種で調査対象）。呼び出し側（スケジューラ等）は「0以外は失敗」と扱う。3 の通知は取込処理自身が Slack critical へ送る（呼び出し側での別途通知は不要）。再開（§3）は 429 の原因確認後に行い、通知は Slack critical に決定済み。停止フラグは 429 が稀なため当面実装せず、発生時に人間が手動で対応する。

補填の1日あたり予算（2026-10-25 固定。人間承認済み）: minute は1日あたり実行時間 2時間まで（実測約170秒/日 → 約40日分）。
1年分（約245営業日）は約11.6時間で、約6営業日で追いつく。日次更新の枠を圧迫しないこと（公式レート上限は未確認）を前提とする。
daily は1日分が数秒のため、同じ予算の範囲内で扱う。実測が増えたら見直す。

### 2-2. 契約範囲の自前判定（Issue #27）
- 実測（2026-10-25, #12）: 日足 開始日 2021-10-25 は取得可・前日は 400、分足 開始日 2024-10-25 は取得可・前日は 400。範囲は日々ローリングする。
- 取得可能な最古日 = 実行日の N 年前の同月同日（日足 N=5、分足 N=2）。その日を含み、実行日まで。2/29 の N 年前が無い場合は 3/1 に寄せる（範囲外を投げない側。未実測）。
- 範囲外の日付は API に投げない。補填の日付計画は範囲内に絞り、古い日から並べる。
- 実装: `src/domain/jquants_contract_range.py`（純関数。定数 `CONTRACT_YEARS` がここに集約）。契約が変わったらこの定数を更新する。
- 400 の分類: 範囲内なら `UNEXPECTED_400_IN_RANGE`、範囲外なら `OUT_OF_CONTRACT_RANGE`。HTTP クライアントは分類せず（infrastructure はロジックを持たない）、application が日付と併せて判定する。
- 補填ジョブへの組み込みは Issue #49 で実装済み（上記の関数は `run_jquants_backfill` から使う。400 の行の動きは `decide_after_day` が担う）。
- 前提: 範囲は「実行日の N 年前の同月同日」という暦年ルールで決め打ち（実測は 2026-10-25 の1点のみ）。契約・仕様が変わったら見直す。
- 日付またぎ（#24 で実装・テスト）: `today` は JST の実行日とし、呼び出し側が渡す。補填は古い日から進めるため先頭が境界ぎりぎりになり、深夜0時をまたぐと計画時は範囲内でも送信時に範囲外になり得る。リクエスト直前に今日の日付で再判定し、範囲外ならスキップする（400 を待たず、No-Go にしない）。サーバー側の「今日」が JST か UTC かは未確認（JST 判定は安全側）。

### 2-1. 停止状態の保持
「停止（フラグ保持）」は、次のスケジュール実行が無視しないよう停止フラグ（ファイル等、Git管理外）で保持する。
フラグは人間が原因確認後に解除する。
**決定（Issue #49、人間承認済み）**: フラグは Git 管理外の JSON（`backfill_state.json`）に、範囲（`BACKFILL_FLAG`=補填のみ / `ALL_FLAG`=全ジョブ）・理由コード・設定日だけを持つ。解除は `python -m src.entrypoints.run_jquants_backfill --clear-stop-flag`（人間のみ。自動解除なし。解除時もロックを取得し、補填の実行中は解除できない）。状態ファイルが壊れている・書き込めない場合は初期化・続行せず失敗として止まる。補填は範囲に関わらずフラグがあれば開始しない。
当日停止は日付つきで同じファイルに残し、翌日は妨げない。直近3回の当日停止が別々の日で同一原因なら `BACKFILL_FLAG`（`REPEATED_TODAY_STOP`）を立てる（「3営業日連続」は補填が走った日で数える。直近3回の走行日がすべて同一原因の当日停止のときだけ立て、間に成功した走行日が挟まれば履歴を消して数え直す。ユーザー承認済み(案A)。履歴は dataset 別（日足/分足）に持つ（人間承認済み））。連続 FAILED は dataset ごとに日付をまたいで数え、COMPLETE/ATTENTION で 0 に戻す。台帳のスキーマは変えない。
補填の403・400（範囲内外とも。範囲内で送った日の400は常に `UNEXPECTED_400_IN_RANGE`）・未知statusの日付は状態ファイルの要確認リストに入れ、次回以降の補填対象から外す（400の扱いは決定・人間承認済み。`review_excluded` として出力）。範囲内400・未知statusが同一原因で3走行日連続（dataset別。間に成功した走行日が挟まれば数え直す）したら、系統的な不具合として `BACKFILL_FLAG`（`REPEATED_REVIEW_STOP`）を立て、人間の確認を必須とする（N1。人間承認済み）。なお、止まった走行の途中にあった成功日は数え直しの対象にしない（数え直すのは COMPLETED/BUDGET_EXHAUSTED で終わった走行のみ。安全側。N2）。

要確認リストは `python -m src.entrypoints.manage_jquants_backfill_review list [--dataset daily|minute]` で読み取り専用の一覧を出し、`clear --dataset <daily|minute> --date <YYYY-MM-DD> --reason-code <code>` で対象1件を解除する。解除は全体ロックを取得できる場合だけ行い、実行中なら状態を変更せず失敗する。解除成功と監査記録は同じ状態ファイルへ原子的に保存し、`review_clear_audit` に dataset ごとに解除対象日・操作日（JST）・理由コードのみを記録する。一覧表示や失敗した解除は監査記録を追加しない。停止フラグの解除は別操作の `--clear-stop-flag` が必要。

補填の dry-run と実行結果 JSON は `stop_flag` を含む。設定済みの場合は scope・reason・set_on、未設定の場合は `null` を出力する。

## 3. 再開（recovery）手順

1. 次の2つを確認する。
   - `list_incomplete_datasets()`: PENDING/RUNNING/PARTIAL/FAILED
   - `list_attention_datasets()`: EMPTY_UNKNOWN/EMPTY_HELD など公開済みだが要確認のもの
2. RUNNING は稼働中でないこと（ロック取得可否）を確認する。ロック取得失敗なら触らない。
3. 原因を記録（機密なし）してから、同一 `--date` を `--refresh` で再実行する。
4. 旧世代は成功確定まで保持される（設計書17）。失敗時は旧公開世代のまま「要確認」と扱い、成功扱いにしない。
5. raw確定済みでcanonical変換のみ失敗の場合は `--canonical-only`（通信なし）を使う。
6. 補填は「日付ごとの最新試行」を台帳とし、最新試行が COMPLETE 以外のものを再開対象とする。
   ただし、休場日以外で「期待どおりの空」と確認して台帳に理由を記録した日付は再開対象から外す（終了条件）。休場日は台帳に書かず、下記のとおり補填対象から除外する。
   `EMPTY_UNKNOWN` / `EMPTY_HELD` は自動で再取得せず「要確認（attention）」に分ける（既存方針）。再開対象（targets）は未記録・PENDING・PARTIAL・FAILED の日で、RUNNING は取得中（in_progress）として待つ（いつまで待つかは補填の実行主体で決める）。
   営業日カレンダーの出どころは J-Quants `markets/calendar` に決定し、取得・保存は実装済み（設計書19 6-3）。休場（区分0・3）の日は、台帳へ書かずに補填対象から除外する（2026-10-29 決定。台帳は取得試行の記録であり、取得していない日の記録を混ぜない。台帳の状態・スキーマは変えない）。
   `python -m src.entrypoints.list_jquants_backfill --dataset <daily|minute> --from <日付> --to <日付>`（通信なし）が、期間内の各日を 対象（targets）/休場（holidays）/取得済み/取得中/要確認（空結果）/契約範囲外 に分けて日付のみ出力する。区分3は休場扱い。営業日でデータが無い日は休場にしない。台帳の読み取りは記録の追加・状態変更をしない（初回はDBの作成・移行が走ることがある）。カレンダー不足の判定は期間全体にかかるため、`--from` が契約範囲より古い場合もカレンダーを覆っている必要がある。`--to` が今日より先の日は契約範囲外として表示する（未来はまだ取れない）。出力には `summary`（件数。`holiday_with_ledger` は `holidays` の内数なので、全項目の合計は日数と一致しない）と、休場日に台帳記録がある場合の `warnings` を含む。
   カレンダーが期間を覆わない場合は失敗し、暗黙に営業日・休場扱いしない。休場日に台帳の記録がある場合は変更せず `holiday_with_ledger` で警告する。実装は domain `jquants_backfill_plan.py`、application `jquants_backfill_planner.py`。
   補填由来の403は「403要確認」として、人間が確認するまで再開対象から外す（§2）。

注意: データ公開前の早い時刻に実行して空の結果が公開された場合（EMPTY_UNKNOWN）は、通常の再実行では取り直されない。
休場日の正当な空と未公開による空の区別は営業日カレンダー（設計書19 6章）で行う。日次の実行時刻は 17:00 に確定（§1-2）。

## 4. Go / Hold / No-Go 基準（metrics JSON 基準）

入力: `data/jquants/metrics/<dataset>/date=<date>/*.json`（既定。`JQUANTS_EXECUTION_METRICS_DIRECTORY` で変更可）。
集計ツールの判定は「部分判定（partial_verdict）」で、下表の実装済み項目だけを評価する。
未評価の項目は `not_evaluated` 列に出す。部分判定が Go でも設計上の Go を意味しない。

| 指標 | Go | Hold | No-Go | 実装 |
|---|---|---|---|---|
| status | COMPLETE | ATTENTION | FAILED / 不正値 | ○ |
| HTTP 401/403 | 0件 | - | ≥1件 | ○ |
| HTTP 400 | 0件 | - | ≥1件 | ○ |
| リクエスト系メトリクス | 計測済み | 未計測・不正値 | - | ○ |
| 429 回数 | 0 | 1–2 | ≥3 | ○ |
| 429以外のリトライ回数（retry_count − 429回数） | 0–2 | 3–9 | ≥10 | ○ |
| 所要時間（wall-clock の total） | ≤ 上限の70% | 70–100%、または上限未設定 | > 上限 | ○ |
| 警告（重複conflict, 要確認） | duplicates_conflict=0 | 警告が過去中央値の2倍超 | 品質検証失敗 | 未（metricsに項目なし） |
| 未許可の未知項目 | 0 | ≥1 | - | 未 |
| 銘柄数 | 対象日の前後の営業日と比べて ±10% | ±10–30% | ±30%超（かつ原因不明） | 未 |
| 空き容量 | §4-1 | §4-1 | §4-1 | ○（実行前の空きを metrics に記録。§4-1 実装記録） |

- 429・リトライは、1日分のリクエスト数が少なく比率が不安定なため回数で判定する（比率は使わない）。
- 所要時間は wall-clock の total で判定する。`wait_seconds` はペーシング・429待機・5xx/通信エラーのバックオフの合計で
  内訳を分けられないため、差し引かない。参考として `total − wait_seconds` を `active_seconds` 列に出す（判定には使わない）。
  429待機で上限を超える場合は上限の設定側で吸収する。
- 所要時間の上限は運用側の持ち時間で決め、日足/分足別にCLIで指定する（未指定は Hold）。
- 通信ゼロの実行（既存データ再利用・`--canonical-only`）は API 健全性を評価できないため `API_HEALTH` を未評価にする。
- 所要時間の上限（2026-10-25 に実測4回を根拠に固定。人間承認済み）:
  daily は 60 秒（Hold は 42 秒超）、minute は 600 秒（Hold は 420 秒超）。
  実測は daily 3.4秒、minute 155〜177秒（429・リトライは0回）。上限は実測の約18倍（daily）・約3.4倍（minute）で、
  minute は 429待機（既定120秒）を2〜3回吸収できる。429・その他リトライの回数閾値は実測0回のため変更しない。
- 実測は各 dataset 数回分の初期値である。実行が10回程度たまった時点で見直す。
- サイズ上限は固定しない（実測: minute 1実行あたり raw 約59〜65MB + canonical 約8MB、1年分で約16GB）。

### 4-1. ディスク基準
基準を1つに統一する: 空き容量が「直近の同 dataset の raw+canonical サイズ×3」未満なら Hold、「×1.5」未満なら全停止。
絶対値（GB）は判定基準としては固定しない。
ただし過去補填に限り、空き容量が 10GB 未満なら補填のみ停止する（日次更新は止めない）。
根拠: 実測の空きは約45GB（増設前）、minute 1年分の raw は約16GB。

**実装（Issue #24）**:
- 測定: 各実行の開始前に、raw / canonical の保存先ボリュームの空きを測り、metrics JSON に `disk_free_bytes_raw` / `disk_free_bytes_canonical` / `disk_same_volume` として数値のみ記録する（パス・自由文字列は出さない）。集計側は metrics だけを読み、FS には触れない。
- 判定: 基準サイズはその実行の `raw_size_bytes` / `canonical_size_bytes`。0（失敗等で未確定）の場合は §4-2 #4 の実測既定値（daily: raw 約1MB・canonical 約0.2MB、minute: raw 約65MB・canonical 約8MB）を使う。同一ボリュームは raw+canonical を合算して判定し、別ボリュームはそれぞれ判定して悪い方を採用する。空き < ×1.5 は No-Go（`DISK_SPACE_CRITICAL`）、< ×3 は Hold（`DISK_SPACE_LOW`）。
- 旧形式・項目欠落・不正値の metrics は DISK_SPACE を未評価のままにする（Go とはみなさない）。このため旧 metrics を含む行の `evaluation_complete` は False のまま。
- 補填のみの空き10GB下限と補填見積りの確認: 判定関数（`backfill_may_start`）を #49 で補填ジョブへ配線した（各日の取得前に、直近1日の raw/canonical サイズ（初回は実測既定値）で判定。同一ボリュームは合算、別ボリュームは個別）。下限割れは補填のみ停止フラグ、×1.5 未満は全停止フラグ、×3 未満は Hold（予算縮小）。
- 空きは実行前、サイズは実行後の値のため、実行中に空きが減る分は次回の判定に反映される。
- 測定はロック取得前に行う。dataset ごとのロックのため daily と minute が同時に動くと測定値が多少ずれるが、×1.5/×3 の余裕で許容する。
- 容量由来の No-Go（`DISK_SPACE_CRITICAL`）はその実行1件の記録で、容量を空けても過去行は変わらない。次回実行の測定値で新しい行が評価される。過去の No-Go を `--fail-on-no-go` から外す手段は §9-1 の未決事項に従う。
- Windows の `st_dev` はドライブごとに異なる値になることを実機で確認済み（C: と D:）。区別できない環境でも同一ボリューム扱い（合算で厳しめ）になり、安全側に倒れる。

### 4-2. 容量対策の方針（Issue #28。方針は案・人間承認待ち。保存先の増設は決定・実施済み＝§4-3）

見積り（#12）: 日足5年 raw 約1.3GB、分足2年 raw 約30GB / canonical 約4GB、合計約36GB。増設前は空き約45GB − 下限10GB = 使える約35GB で余裕がなかった。分足は毎年 raw 約16GB 増える（約65MB × 約245営業日）。

**判定の分担**: 本節は基準（何を測り、どの値で止めるか）を定める。`DISK_SPACE` を判定・集計へ組み込む実装は #24 で実施済み（§4-1 実装）。

1. **保存先**: raw / canonical は `JQUANTS_RAW_DIRECTORY` / `JQUANTS_CANONICAL_DIRECTORY` で場所を指定できる（コード変更不要）。補填開始前に、使える容量（空き − 補填下限）が補填見積りを上回る保存先へ切り替える。ただし、データ取得済みの dataset で保存先を切り替える場合は、先に既存データを新しい保存先へ移し、件数・ハッシュで整合を確認してから環境変数を切り替える（移動前の切替は、取得済みファイルが見えなくなり再開・冪等性を壊す）。raw と canonical は別ドライブでもよい。保存先はいずれも Git 管理外で、`trade-report` へは出さない（§6）。
   - 移す対象は4つ: raw、canonical、台帳（`JQUANTS_LEDGER_DATABASE_FILE`）、実行メトリクス（`JQUANTS_EXECUTION_METRICS_DIRECTORY`。Go/No-Go 判断と閾値見直しの一次記録でバックアップ対象のため、データと同じ場所に置く）。既定値はいずれも従来の `data/jquants/...` のまま。
   - **台帳は `store_settings.raw_directory` に raw の絶対パスを記録し、不一致だと `INITIALIZATION_ERROR` で停止する**。移行では台帳も移し、コピー側の `raw_directory` を新しい正規化パスへ更新する（更新前に `.bak` を取る）。
   - 目安容量: 補填約36GB + 日次5年分約90GB + 下限・余裕約20GB で約150GB 以上。
   - 実施記録は §4-3。
2. **保持方針（案）**:
   - 日足 raw: 小さい（5年で約1.3GB）ため長期保持する。
   - 分足 raw: 直近 N 日分（N は人間が決定。未決）のみ raw のまま保持する。N 日を超えた世代は圧縮してよいが、元ファイルの置換は削除と同義のため次の削除条件と同じ前提を満たすこと。圧縮後に伸長して元とハッシュ一致を確認するまで元を残し、圧縮中は両方が存在する分の一時容量を確保する。
   - 分足 raw の削除は、canonical が検証済み（品質検証成功・§4 で Go）で、かつ別の保存先にバックアップ（§7）がある場合に限る。契約範囲はローリング（§2-2）で、削除後に再取得できない恐れがあるため、不可逆な削除はこの条件を満たすまで行わない。
   - canonical（parquet+zstd）は削除しない。
   - 削除・圧縮の実行処理は #28 では実装しない（別 Issue。人間承認後）。
3. **補填の順序と範囲（段階補填）**: 日足5年 → 分足の順に補填する。日付の順序は §2-2（古い日から。契約範囲の古い端はローリングで失われるため先に確保する）に従う。新しい日付から遡る案は、古い日が範囲外になり取得不能になりうるため採用しない（人間が別途決める場合のみ変更）。1回の補填で追加するサイズは「空き − 補填下限」を超えない範囲に制限し、容量が足りない場合は取得済み範囲までで止めて（PARTIAL）、保存先の拡張後に再開する。
4. **停止条件**: §4-1 の相対基準（×3 Hold / ×1.5 全停止）と、補填のみの空き10GB下限は維持する。補填の開始前には、追加見積りサイズ（直近の1日あたり raw+canonical × 補填予定営業日数）が「空き − 10GB」以内であることも確認する。初回（直近サイズ不明）は見積りに #12 の実測（日足は5年 raw 約1.3GB ÷ 約1,215営業日 ≒ 約1MB/日、分足は raw 約65MB + canonical 約8MB/日）を使う。raw と canonical を別ボリュームに置く場合は、ボリュームごとに判定する（raw の見積りは raw 側、canonical の見積りは canonical 側の空きに対して。§4-1 の相対基準も各ボリュームの空きに対し、そのボリュームに置くサイズで判定し、いずれか悪い方を採用する）。
5. **チェック時点**: 各実行の開始前（補填は各日付の取得前）。
6. **公開境界**: 有料データを公開レポートへ出さない制約は変更しない。圧縮・移動・バックアップ先のいずれも公開リポジトリ・`trade-report` の対象外。

## 5. 実行サマリの蓄積

- metrics JSON を一次情報とし、実行ごとの行（status, partial_verdict, reasons, not_evaluated, 最新試行か, 連続FAILED数, requests, 429, elapsed各種, size）をCSVに集計する。
- 集計出力は Git 管理外（既定の設定では `data/jquants/metrics_summary.csv`。metrics ディレクトリを変えた場合はその親、§4-3）。出力する値は検証済みの数値と列挙コードのみで、
  株価レコード・銘柄コード・自由文字列は含めない。
- No-Go を `--fail-on-no-go` で終了コードにできる。ただし metrics が0件でも終了コードは0なので、
  「実行が1件も無い」ことの検知には最新 metrics の鮮度チェックが別途必要。
- 連続FAILEDは2列: `consecutive_failed_same_date`（同一日付の再試行）と `consecutive_failed_dataset`（dataset内、ファイル名の時刻順）。
- `active_seconds` は `wait_seconds` が未計測のとき空欄。

## 6. データ利用側との契約（案）

詳細は [19 canonical schema運用ルールとデータ利用側の入力契約](./19-jquants-consumer-contract.md) が正で、以下は最小の要約（Issue #10）。入力契約の項目・欠損日の扱い・併用の可否は19を参照する。

- canonical schema は version を持ち、破壊的変更は禁止（追加のみ。追加でも版を上げる）。
- 利用側は入力契約（19の3章）に従い、欠損・未取得日は明示する。
- Yahoo/自前データへの暗黙フォールバックは禁止（併用は当面認めない。19の4章）。
- `trade-report` へは有料データ生値・復元可能な派生を出さない（`docs/architecture/public-report-publication.md`）。

## 7. バックアップ

有料データはGit管理外で唯一のコピーになりうる。契約が切れると再取得できない可能性がある。

- バックアップ先: 外付け SSD（E:）。初回は 2026-10-27 に取得済み（D: とハッシュ一致を確認）。対象は raw / canonical / 台帳 / metrics。
- 次回以降の頻度と整合性確認の方法は未決（判断待ち、§9）。
- 台帳（SQLite）は書き込み中にコピーしない。実行が止まっている間にコピーするか、SQLite のバックアップ機能を使う。ハッシュ一致はコピーが元と同一だったことの確認で、書き込み途中でなかったことの保証ではない。
- 台帳は raw の絶対パスを記録するため、バックアップから戻す場合は `store_settings.raw_directory` を戻し先の正規化パスへ更新する（更新前に `.bak` を取る）。
- E: は USB 接続でドライブ文字が変わりうるため、バックアップ手順はボリューム名等で探せるようにする。

## 8. テスト観点

- 優先度: 日次が未完了のとき補填が開始されない。
- ロック競合時に処理を奪わずスキップする。
- 429回数・連続失敗・ディスク閾値で補填が止まり、日次は継続（または停止）する。
- 判定関数: 境界値（429が1/3回、他リトライ3/10回、所要時間70%/100%）、未設定・未計測・不正値、通信ゼロ。
- 取得処理が実際に書くmetrics JSONを集計に通す結合テスト（フィールド名の変更を検知）。
- 再開: PARTIAL/FAILED → 再実行で旧世代保持、成功後に公開。
- 機密: ログ/サマリにAPIキー・ページキー・生レスポンス・銘柄コード・自由文字列が含まれない。

- **補填完了の定義（決定・人間承認済み）**: 計画の対象（targets）が空で、要確認（空結果）・403/範囲外の要確認・取得中が残らない状態を `COMPLETED`。残る場合は `COMPLETED_WITH_REVIEW`（人間の確認待ち）。1日予算・`--max-days` で止まれば `BUDGET_EXHAUSTED`（次回継続）。
- **「補填由来の日付」の判定（決定・人間承認済み）**: 台帳には持たず、補填ジョブが処理した日付として扱う（403・範囲外400は補填ジョブの状態ファイルで管理）。日次ジョブ側の再開（§3）が補填由来の403日付を再実行しないよう、日次配線時に要確認リストを参照する。
- 補填の1日予算の Hold 縮小率は 50%（初期値・人間承認済み）。429 は1件でも当日停止、非429リトライ≥10・所要時間超過も当日停止、リトライ3〜9・所要70%超は Hold（予算縮小）。
