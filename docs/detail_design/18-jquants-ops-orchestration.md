# J-Quants 運用オーケストレーション設計（案）

状態: 提案（未実装・判断待ちあり）。前提: 設計書15/16/17、`runbook_jquants_pilot_one_day.md`。
本書は単日取込CLI（`ingest_jquants_single_day`）を日次運転・過去補填へ拡張する際の運用ルールを定める。
閾値はすべて初期値で、パイロット実測後に見直す。
第三者レビュー（PR #14）の指摘を反映済み。

## 1. ジョブ種別と優先度

| 優先 | ジョブ | 内容 |
|---|---|---|
| P0 | 日次更新 daily | 直近営業日の日足 |
| P0 | 日次更新 minute | 直近営業日の分足 |
| P1 | 再開 recovery | 未完了・要確認データセットの再実行（§3） |
| P2 | 過去補填 backfill | 契約境界（日足 2021-10-21、分足 2024-10-21）まで新しい日付から遡る |

ルール:
1. 日次更新は常に補填より優先する。
2. 補填は日次更新が完了済み、かつ当日の1日あたり予算内の場合のみ実行する。
3. 補填は1日分（dataset×date）を最小単位とし、新しい日付から遡る。
4. 日足と分足は同時に走らせない。日次では 日足 → 分足 の順。
5. データセットロックを取得できない場合は待機せず、そのジョブをスキップして記録する（処理を奪わない）。

### 1-1. 同時実行の防止
既存のロックは dataset×date 単位で、レート制限もプロセス内に閉じている。
日足/分足、日次/補填、手動パイロットが別プロセスで重なると同一APIキーへのリクエストが倍増し429の原因になる。
実行基盤で「実行中なら新規開始しない」設定にするか、全体ロック（APIキー単位）を置く。方式は判断待ち（§8）。

## 2. 停止・減速条件（API枠制御）

動作はジョブ種別ごとに定める（○=継続、×=当日停止）。

| 条件 | 日次 | 再開 | 補填 | 備考 |
|---|---|---|---|---|
| 401 | × | × | × | 全停止。停止状態を保持（§2-1）。人間判断で再開 |
| 403（契約範囲内の日付） | × | × | × | 全停止。人間判断で再開 |
| 403（契約範囲外の日付） | - | - | 補填を終了 | 補填が契約境界に到達した扱い。範囲の動き方は公式仕様の確認待ち |
| 429（metrics上で1回以上） | ○ | ○ | 当日停止を検討 | Hold。3回以上は No-Go |
| 連続FAILED 3回（同一 dataset/date） | 当日停止 | 当日停止 | 当日停止 | 人間へ通知 |
| ディスク空き不足（§4-1） | × | × | × | 全停止 |
| 未許可の未知項目 | 当該ジョブのみ停止 | 同左 | 同左 | ExRT/MktCap は記録のみ |
| 品質検証失敗 | 当該ジョブ停止 | 同左 | 以降の日付も停止 | No-Go |

「429 再試行枯渇」と「PARTIAL」は、現状の metrics JSON（status は COMPLETE/ATTENTION/FAILED のみ）では区別できない。
旧世代を保持した PARTIAL は FAILED でなく ATTENTION（Hold）になるため、区別できるよう metrics JSON に
`error_category` と実行モード（`raw_source`）を追加する（別Issueで対応）。

補填の1日あたり予算（初期案）: 最大N日分/実行時間上限。Nは実測の所要時間から決める（判断待ち）。

### 2-1. 停止状態の保持
「全ジョブ停止」は、次のスケジュール実行が無視しないよう停止フラグ（ファイル等、Git管理外）で保持する。
フラグは人間が原因確認後に解除する。方式は判断待ち（§8）。

## 3. 再開（recovery）手順

1. 次の2つを確認する。
   - `list_incomplete_datasets()`: PENDING/RUNNING/PARTIAL/FAILED
   - `list_attention_datasets()`: EMPTY_UNKNOWN/EMPTY_HELD など公開済みだが要確認のもの
2. RUNNING は稼働中でないこと（ロック取得可否）を確認する。ロック取得失敗なら触らない。
3. 原因を記録（機密なし）してから、同一 `--date` を `--refresh` で再実行する。
4. 旧世代は成功確定まで保持される（設計書17）。失敗時は旧公開世代のまま「要確認」と扱い、成功扱いにしない。
5. raw確定済みでcanonical変換のみ失敗の場合は `--canonical-only`（通信なし）を使う。
6. 補填は「日付ごとの最新試行」を台帳とし、最新試行が COMPLETE 以外のものを再開対象とする。

注意: データ公開前の早い時刻に実行して空の結果が公開された場合（EMPTY_UNKNOWN）は、通常の再実行では取り直されない。
休場日の正当な空と未公開による空の区別、営業日カレンダーの出どころ、日次の実行時刻を決める必要がある（§8）。

## 4. Go / Hold / No-Go 基準（metrics JSON 基準）

入力: `data/jquants/metrics/<dataset>/date=<date>/*.json`。
集計ツールの判定は「部分判定（partial_verdict）」で、下表の実装済み項目だけを評価する。
未評価の項目は `not_evaluated` 列に出す。部分判定が Go でも設計上の Go を意味しない。

| 指標 | Go | Hold | No-Go | 実装 |
|---|---|---|---|---|
| status | COMPLETE | ATTENTION | FAILED / 不正値 | ○ |
| HTTP 401/403 | 0件 | - | ≥1件 | ○ |
| リクエスト系メトリクス | 計測済み | 未計測・不正値 | - | ○ |
| 429 回数 | 0 | 1–2 | ≥3 | ○ |
| 429以外のリトライ回数（retry_count − 429回数） | 0–2 | 3–9 | ≥10 | ○ |
| 実質所要時間（total − wait_seconds） | ≤ 上限の70% | 70–100%、または上限未設定 | > 上限 | ○ |
| 警告（重複conflict, 要確認） | duplicates_conflict=0 | 警告が過去中央値の2倍超 | 品質検証失敗 | 未（metricsに項目なし） |
| 未許可の未知項目 | 0 | ≥1 | - | 未 |
| 銘柄数 | 対象日の前後の営業日と比べて ±10% | ±10–30% | ±30%超（かつ原因不明） | 未 |
| 空き容量 | §4-1 | §4-1 | §4-1 | 未 |

- 429・リトライは、1日分のリクエスト数が少なく比率が不安定なため回数で判定する（比率は使わない）。
- 429待機（`JQUANTS_429_WAIT_SECONDS`）は運用上の待ちなので、所要時間判定から除く。
- 所要時間の上限は運用側の持ち時間で決め、日足/分足別にCLIで指定する（未指定は Hold）。
- 通信ゼロの実行（既存データ再利用・`--canonical-only`）は API 健全性を評価できないため `API_HEALTH` を未評価にする。
- 時間上限・サイズ上限は初回パイロット実測後に固定する（判断待ち）。

### 4-1. ディスク基準
基準を1つに統一する: 空き容量が「直近の同 dataset の raw+canonical サイズ×3」未満なら Hold、「×1.5」未満なら全停止。
絶対値（GB）は固定しない。

## 5. 実行サマリの蓄積

- metrics JSON を一次情報とし、実行ごとの行（status, partial_verdict, reasons, not_evaluated, 最新試行か, 連続FAILED数, requests, 429, elapsed各種, size）をCSVに集計する。
- 集計出力は Git 管理外（`data/jquants/metrics_summary.csv`）。出力する値は検証済みの数値と列挙コードのみで、
  株価レコード・銘柄コード・自由文字列は含めない。
- No-Go を `--fail-on-no-go` で終了コードにでき、スケジューラから利用できる。

## 6. データ利用側との契約（案）

- canonical schema は version を持ち、破壊的変更は禁止（追加のみ、変更時は新バージョン）。
- 利用側は (dataset, schema_version, 期間, 欠損日リスト) を入力契約とし、欠損・未取得日は明示する。
- Yahoo/自前データへの暗黙フォールバックは禁止。必要なら明示オプションのみ。
- `trade-report` へは有料データ生値・復元可能な派生を出さない（`docs/architecture/public-report-publication.md`）。

## 7. バックアップ

有料データはGit管理外で唯一のコピーになりうる。契約が切れると再取得できない可能性がある。
バックアップ先・頻度・整合性確認の方針を決める（判断待ち、§8）。

## 8. テスト観点

- 優先度: 日次が未完了のとき補填が開始されない。
- ロック競合時に処理を奪わずスキップする。
- 429回数・連続失敗・ディスク閾値で補填が止まり、日次は継続（または停止）する。
- 判定関数: 境界値（429が1/3回、他リトライ3/10回、所要時間70%/100%）、未設定・未計測・不正値、通信ゼロ。
- 取得処理が実際に書くmetrics JSONを集計に通す結合テスト（フィールド名の変更を検知）。
- 再開: PARTIAL/FAILED → 再実行で旧世代保持、成功後に公開。
- 機密: ログ/サマリにAPIキー・ページキー・生レスポンス・銘柄コード・自由文字列が含まれない。
