# J-Quants 運用オーケストレーション設計（案）

状態: 提案（未実装・判断待ちあり）。前提: 設計書15/16/17、`runbook_jquants_pilot_one_day.md`。
本書は単日取込CLI（`ingest_jquants_single_day`）を日次運転・過去補填へ拡張する際の運用ルールを定める。
コード変更は含まない。閾値は初期値で、パイロット実測後に見直す。

## 1. ジョブ種別と優先度

| 優先 | ジョブ | 内容 |
|---|---|---|
| P0 | 日次更新 daily | 直近営業日の日足 |
| P0 | 日次更新 minute | 直近営業日の分足 |
| P1 | 再開 recovery | PENDING/RUNNING(死活切れ)/PARTIAL/FAILED の再実行 |
| P2 | 過去補填 backfill | 契約境界（日足 2021-10-21、分足 2024-10-21）まで新しい日付から遡る |

ルール:
1. 日次更新は常に補填より優先する。同時実行しない（単一ワーカー直列）。
2. 補填は日次更新が完了済み、かつ当日の1日あたり予算内の場合のみ実行する。
3. 補填は1日分（dataset×date）を最小単位とし、新しい日付から遡る。
4. 日足と分足は同時に走らせない。日次では 日足 → 分足 の順。
5. データセットロックを取得できない場合は待機せず、そのジョブをスキップして記録する（処理を奪わない）。

## 2. 停止・減速条件（API枠制御）

| 条件 | 動作 |
|---|---|
| 401 / 403 / 契約範囲外 | 即停止。全ジョブ停止（No-Go）。人間判断で再開 |
| 429 | 既存リトライ/待機に従う。1ジョブで429率 > 5%（初期値）なら補填を当日停止 |
| 429 再試行枯渇 | そのジョブ FAILED。補填は当日全停止、日次のみ翌日再試行 |
| 連続FAILED 3回（同一 dataset） | 当日そのdatasetを停止し人間へ通知 |
| ディスク空き < 閾値（例: 10GB） | 全ジョブ停止 |
| 未許可の未知項目 | Hold。当該ジョブのみ停止（ExRT/MktCap は記録のみ） |
| 品質検証失敗 | No-Go。補填の以降の日付も停止 |

補填の1日あたり予算（初期案）: 最大N日分/実行時間上限。Nは実測の所要時間から決める（判断待ち）。

## 3. 再開（recovery）手順

1. `list_incomplete_datasets()` で PENDING/RUNNING/PARTIAL/FAILED を列挙する。
2. RUNNING は稼働中でないこと（ロック取得可否）を確認する。ロック取得失敗なら触らない。
3. 原因を記録（機密なし）してから、同一 `--date` を `--refresh` で再実行する。
4. 旧世代は成功確定まで保持される（設計書17）。失敗時は旧公開世代のまま「要確認」と扱い、成功扱いにしない。
5. raw確定済みでcanonical変換のみ失敗の場合は `--canonical-only`（通信なし）を使う。
6. 補填は「日付ごとの最新試行ステータス」を台帳とし、COMPLETE 以外を再開対象とする。

## 4. Go / Hold / No-Go 定量基準（metrics JSON 基準）

入力: `data/jquants/metrics/<dataset>/date=<date>/*.json`。

| 指標 | Go | Hold | No-Go |
|---|---|---|---|
| status（metrics JSON） | COMPLETE | ATTENTION（EMPTY_UNKNOWN/EMPTY_HELD等の警告を含む） | FAILED（PARTIAL含む） |
| HTTP 401/403 | 0 | - | ≥1 |
| 429 率（429件/requests） | ≤1% | 1–5% | >5% または再試行枯渇 |
| retries_total / requests | ≤5% | 5–20% | >20% |
| 総所要時間（elapsed_total） | ≤ 上限の70% | 70–100% | > 上限 |
| 警告（重複conflict, 要確認） | duplicates_conflict=0 | 警告が過去中央値の2倍超 | 品質検証失敗 |
| 未許可の未知項目 | 0 | ≥1 | - |
| 銘柄数 | 直近5営業日中央値の±10% | ±10–30% | ±30%超（かつ原因不明） |
| 空き容量 | ≥ 推定サイズ×3 | ≥ ×1.5 | それ未満 |

時間上限・サイズ上限は、日足/分足それぞれ初回パイロット実測値を基準に固定する（判断待ち）。
dataset別（日足/分足）に基準を分け、取得/変換/検証の各 elapsed を比較してボトルネックを可視化する。

## 5. 実行サマリの蓄積

- metrics JSON を一次情報とし、日付×datasetの1行サマリ（status, requests, 429, elapsed各種, size, 判定）を集計する。
- 集計出力は Git 管理外 (`data/jquants/metrics/`配下)。株価レコード・銘柄コード・生値は含めない。
- 集計用の最小コード案: `metrics` を走査して表/CSV化し、上記基準で判定するだけの読み取り専用スクリプト。

## 6. データ利用側との契約（案）

- canonical schema は version を持ち、破壊的変更は禁止（追加のみ、変更時は新バージョン）。
- 利用側は (dataset, schema_version, 期間, 欠損日リスト) を入力契約とし、欠損・未取得日は明示する。
- Yahoo/自前データへの暗黙フォールバックは禁止。必要なら明示オプションのみ。
- `trade-report` へは有料データ生値・復元可能な派生を出さない（`docs/architecture/public-report-publication.md`）。

## 7. テスト観点

- 優先度: 日次が未完了のとき補填が開始されない。
- ロック競合時に処理を奪わずスキップする。
- 429率/連続失敗/ディスク閾値で補填が止まり、日次は継続（または停止）する。
- 判定関数: 境界値（1%/5%、±10%/±30%）の単体テスト（合成metricsのみ、ネットワーク不使用）。
- 再開: PARTIAL/FAILED → 再実行で旧世代保持、成功後に公開。
- 機密: ログ/サマリにAPIキー・ページキー・生レスポンス・銘柄コードが含まれない。
