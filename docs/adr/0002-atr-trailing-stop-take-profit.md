# ADR-0002: ATRトレーリングストップによる利確ロジックの追加

## ステータス

実装済み / 2026-09-25

## 背景・課題

現状の決済ロジック(`TradeSignal.evaluate`)は以下の2種類のみで、いずれも下落方向の
条件でしか発火しない。

- 通常決済(`regular_exit`): 現在値 ≦ SMA5×0.99(lower_band) かつ RSI14 ≦ 45
- ATR損切り(`atr_exit`): 現在値 ≦ エントリー価格 − ATR×倍率(通常1.5/警戒1.0/危険2.0)

新規買いはSMA上抜け(upper_band)+RSI高値圏というブレイクアウト条件で行われるため、
通常決済が発火するには「上側バンドから下側バンドまで押し戻される」レベルの
大きな反転が同日中に必要で、現実的にはほぼ発生しない。ATR損切りも下落方向にしか
効かないため、**含み益が乗っている間にそれを確定させる利確の手段が存在しない**。

`ALLOW_OVERNIGHT_HOLDING=false`により大引け前に`_liquidate_all_positions()`で
強制決済されるため、ポジションが決済されないまま放置されるわけではないが、
シグナルに基づく決済ではなく、常に成行での日中決済に頼っている状態になっている。

## 決定

保有中の損切り基準(ATR)を、**保有開始後の最高値を基準点とするトレーリングストップ
(シャンデリア・イグジット)**に拡張する。

- 計算式: `現在値 <= (保有開始後の最高値 − ATR×倍率)`
  (既存の損切り計算式の基準点を`entry_price`から「保有中の最高値」に置き換えるだけ)
- 含み益がまだ無い(高値=エントリー価格のまま)場合は、現状と全く同じ挙動(=損切り)になる
- 高値を更新するたびに決済ラインが切り上がり、トレンドが続く限り持ち続け、
  反転し始めたところで利益を確定できる
- レジーム別倍率(通常1.5/警戒1.0/危険2.0)はそのまま流用する

### 保有中最高値の状態管理

3案(①前日までの確定日足ベース、②分足データベース、③ライブ売買ループ内での
リアルタイム状態保持)を比較し、③を採用する。

- ①は当日の値動きを拾えず、デイトレード前提の運用と矛盾するため却下
- ②は分足データ基盤への依存が増え、この用途には過剰なため却下
- ③は追加のデータ基盤なしで十分な精度が出せ、状態も当日限り(大引けで
  必ず決済される)で良いため管理コストが低い

状態はメモリ保持でよいが、ログには売買判定要素として記録する。

### 状態の初期化・クリアのタイミング

SELL・BUYいずれの注文も、最終的に`_register_order`という共通メソッドを経由して
記録される(通常決済・ATR損切り・大引けの強制決済`_liquidate_all_positions`の
いずれも同じ経路)。この1箇所に以下を実装する。

- `signal.side == BUY`のとき: 保有中最高値の初期値を約定価格(`signal.price`)で
  セットする
- `signal.side == SELL`のとき: 対象銘柄の保有中最高値の状態をクリアする

共通化により、将来決済経路が増えても(`_register_order`を通る限り)自動的に
対応される。また買い側で初期化を怠ると、次のループでトレーリング判定をする際に
「値が無い場合の代替処理」が必要になり、代替値の選び方次第で利確ラインの計算が
意図とズレる可能性があるため、買い・売り両方を同じ場所で対にして扱う。

### ログ方針

- 専用のログ経路は新設せず、既存の毎ループ判定ログ(分速ログ)に
  「保有中最高値」「利確ライン(高値−ATR×倍率)」の2項目を追加する
- 毎ループのkeep/buy/sellの詳細ログは削らずDEBUGレベルで維持する
  (2026-09-11の戦略転換の診断も、まさにこの粒度のログがあったことで可能になった実績があるため)
- INFOレベルでは、銘柄ごとの初回判定と判定状態の変化(buy/sell/keep間の遷移)だけを出力する。
  同じ判定が続く間の毎ループ詳細はDEBUGに留め、通常のINFOログの反復を抑える

## 検討した代替案

- **固定%利確**: 却下。トレンド追随という戦略思想と相性が悪く、
  伸びているトレンドを機械的に途中で切ってしまう
- **ATRベース(エントリー価格基準の固定利確ライン)**: 却下。固定%と同様、
  エントリー後どれだけ伸びても上限ラインが動かないため早期に打ち止めになりやすい
- **保有中最高値を分足データで管理**: 却下(前述の通り、現状の用途には過剰)
- **保有中最高値を日足ベースで管理**: 却下(前述の通り、当日の値動きを拾えない)

## 影響・トレードオフ

- `_register_order`に銘柄ごとの状態を初期化・クリアする処理が追加される
- 毎ループの判定ログの項目が増える(ログ量そのものは、ログレベル分離により
  体感の可読性はむしろ改善する見込み)
- 3ヶ月のデータ蓄積フェーズの途中での導入となるため、導入前後でこの部分の
  決済挙動の比較がしづらくなる点は留意する
